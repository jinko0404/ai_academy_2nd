## 2. 결과에 대한 보고서

### 실습 목적

답변을 확인할 때 무엇을 나누어 검사해야 하는지 알아보는 실습이다. 답변 내용이 원본과 같은지, 필요한 항목이 있는지, 출처가 적혀 있는지를 구분했다. 질문과 답변은 사람이 미리 작성한 예시이며, 실제 LLM을 호출하지 않았다.

### F01 · 원본과 답변이 다른 사례

- 원본: “실습 파일은 개인 폴더에 보관합니다.”
- 답변: “실습 파일은 공용 서버 폴더에 보관합니다.”
- 출처 목록: `["K01"]`

출처 항목과 출처 이름은 있지만, 보관 장소가 원본의 ‘개인 폴더’에서 답변의 ‘공용 서버 폴더’로 바뀌었다. 따라서 `factual_mismatch`로 분류되었다. 출처 이름을 적었다는 사실만으로 답변 내용이 맞는다고 판단할 수 없음을 보여 준다.

### F02 · 필수 항목이 없는 사례

- 원본과 답변: “프로젝트 폴더에서 서버를 실행합니다.”
- 출처 목록: `sources` 항목 자체가 없음

답변 문장은 원본과 같지만, 이 실습에서 필수로 정한 `sources` 항목이 빠졌다. 따라서 `format`으로 분류되었다. 내용이 맞아도 프로그램이 요구하는 응답 양식을 지키지 않을 수 있다는 뜻이다.

### F03 · 항목은 있지만 출처가 없는 사례

- 원본과 답변: “오류 메시지와 시도한 작업을 함께 적습니다.”
- 출처 목록: `[]`

`sources`라는 항목은 있으므로 F02와는 다르다. 하지만 목록에 출처 이름이 하나도 없어 `evidence`로 분류되었다. 항목을 만드는 것과 그 안에 필요한 정보를 채우는 것은 별개임을 보여 준다.

### 검사 순서와 한계

코드는 ‘출처 항목 없음 → 출처 목록이 비어 있음 → 답변과 원본 문자열이 다름’ 순서로 검사한다. 먼저 해당하는 문제 하나만 기록하므로, 여러 문제가 있는 답변에서도 모든 문제를 찾아 기록하는 것은 아니다.

또한 문장의 의미를 이해하는 대신 문자열이 같은지만 비교한다. 같은 뜻을 다른 표현으로 쓰더라도 불일치로 표시될 수 있다. 출처 이름이 실제 자료를 가리키는지, 그 자료가 믿을 만한지, 답변을 뒷받침하는지도 확인하지 않는다. 따라서 이 결과는 제공된 세 사례의 규칙 기반 분류 결과이며, 실제 LLM 답변의 사실성을 자동으로 판정한 결과는 아니다.

### 수업 내용과의 연결

| 구성요소 | 이번 검증과 연결되는 역할 |
|---|---|
| FastAPI | 요청과 응답에 필수 항목이 있는지, 정해진 자료형을 지키는지 검사할 수 있다. |
| PostgreSQL | 답변과 비교할 원본 자료를 보관할 수 있다. |
| RAG | 답변을 만들 때 참고할 자료를 찾아 제공한다. 검색된 자료가 있다는 것만으로 답변의 정확성이 보장되지는 않는다. |
| Agent | 도구를 사용해 작업할 때 어떤 동작까지 허용할지 권한을 관리해야 한다. |

위 내용은 향후 시스템에 적용할 수 있는 연결 설명이다. 이번 코드에서 서버, 데이터베이스, RAG, Agent를 실제로 실행한 것은 아니다.

### 실습에서 알게 된 점

답변 내용의 정확성, 응답 형식, 출처 유무는 각각 확인해야 한다. F01은 출처가 있어도 원본과 달랐고, F02와 F03은 답변이 원본과 같아도 형식이나 출처 정보가 부족했다. 실제 서비스에서는 이 검사들을 나누고, 출처의 신뢰성과 답변을 뒷받침하는지까지 추가로 확인해야 한다.
