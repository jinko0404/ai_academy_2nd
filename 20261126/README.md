# PART A. 이번 수업이 기존 공부와 어떻게 연결되는가

## A-1. Day26 → Day27 → Day28 → Day29의 차이

| 수업 | 질문 | 핵심으로 배우는 것 | 대표 흐름 |
|---|---|---|---|
| **Day26 — Basic RAG** | 문서를 찾아 근거 있는 답변을 만들려면? | 검색·Context·Prompt·LLM·출처 검증 | 질문 → Retriever → Context → LLM → 검증 |

| **Day28 — Evaluation** | 검색과 답변이 제대로 됐는지 어떻게 확인하지? | Gold Dataset·평가지표·오류 단계 진단 | Dataset → 실행 → 평가 → 개선 |

**핵심:** Day29는 RAG를 다시 만드는 수업이 아니다. **이미 있는 RAG와 PostgreSQL 조회 기능을 Tool로 등록하고, LLM이 어떤 Tool이 필요한지 제안하도록 만드는 구조**를 배운다.

## A-2. 가장 먼저 외울 한 문장

> **LLM은 어떤 Tool을 사용할지 제안하고, Agent Harness(서버 실행 환경)는 그 제안이 허용되는지 확인한 뒤 실제 Python Tool을 실행한다. 실행 결과를 다시 LLM에 전달하면, LLM이 다음 Tool을 요청하거나 최종 답변을 작성한다.**

**중요한 오해 금지:** ‘LLM이 DB를 직접 조회했다’는 설명은 정확하지 않다. 이 강의 구조에서는 LLM은 도구 호출 요청을 만들고, 서버가 등록된 도구 함수를 실제로 실행한다.

## A-3. 미리 준비된 것과 질문할 때 실행하는 것

### 미리 준비한 기반

- **문서 준비:** Raw → Parsing → Cleaning → Chunk → E5 문서 벡터 → PostgreSQL + pgvector 저장.
- **RAG 검색·생성:** 질문 벡터 생성 → 후보 검색 → Cross-Encoder 재정렬 → Context 선택 → Prompt → LLM → 출처·상태 검증.
- **운영 DB:** 과제 ID와 제출 상태 등의 구조화된 데이터를 PostgreSQL에 저장.
- **Tool 정의:** `rag_search`와 `lookup_status`를 어떤 입력으로 사용할 수 있는지 서버에서 정의.
- **Agent 설정:** Tool을 사용할 수 있는 Chat Model, 실행 한도, 서버 인증 정보 전달 방법을 미리 구성.

### 사용자가 질문할 때 실행하는 것

- 사용자 요청 접수와 인증·입력 검사.
- LLM의 도구 선택 제안.
- 서버의 Tool 이름·입력·권한 검사.
- 필요한 Tool 실제 실행.
- 실행 결과를 LLM에 재전달.
- LLM의 추가 요청 또는 최종 답변 생성.
- 서버의 최종 결과·출처·오류 검증.
- API 응답 반환.

문서 Indexing은 매 질문마다 다시 실행하지 않는다. 반면 **질문이 들어올 때의 Tool 선택과 조회는 요청마다 달라질 수 있다.**

## A-4. 전체 구조를 한눈에 보기

```text
사용자 / 프론트엔드
        │ 질문 전송
        ▼
FastAPI: 요청 검사 + 사용자 인증
        │ 신뢰된 사용자 정보 별도 보관
        ▼
Agent Harness: 실행 시작, 모델·Tool 관리
        │ 메시지 + 사용할 수 있는 Tool 설명
        ▼
LLM: 다음 행동 판단
        │
        ├─ Tool 필요 없음 ────────────────────────┐
        │                                       │
        └─ Tool 호출 제안(tool_calls)            │
                    │                           │
                    ▼                           │
          Harness: 허용 목록·입력 검사            │
                    │                           │
          ┌─────────┴─────────┐                 │
          ▼                   ▼                 │
  rag_search Tool       lookup_status Tool      │
  문서 규정 검색·답변     내 과제 상태 DB 조회      │
          │                   │                 │
          └─────────┬─────────┘                 │
                    ▼                           │
        ToolMessage: 실행 결과 전달               │
                    │                           │
                    ▼                           │
           LLM: 결과 확인·다음 행동 판단 ◄────────┘
                    │
           ├─ 필요하면 Tool 추가 요청 → 반복
           │
           └─ 최종 AIMessage 작성
                    ▼
       서버 Validator: 출처·상태·권한·오류 점검
                    ▼
          FastAPI: 검증된 HTTP 응답
                    ▼
             프론트엔드 → 사용자
```

이 그림은 **가능한 동작 구조**를 보여준다. 모델이 Tool을 몇 개 선택하고 어떤 순서로 실행하도록 요청하는지는 고정되어 있지 않다.

# PART B. 사용자 요청부터 응답까지 — 실제 동작을 24단계로

## B-0. 예시 상황 설정

이후 설명에서는 한 가지 질문을 끝까지 따라간다.

**사용자의 질문**

> “과제 제출 규정은 어떻게 되고, 내 101번 과제는 제출됐나요?”

자료에서 쓰는 교육용 상황은 다음과 같다.

- `rag_search`: 학교·교육센터의 **과제 제출 규정**이 적힌 문서에서 근거를 찾는 Tool.
- `lookup_status`: PostgreSQL에서 **현재 로그인한 사용자의 과제 제출 상태**를 조회하는 Tool.
- 가상 로그인 사용자: `stu-001`.
- 가상 DB 예시: `stu-001`의 `task_id=101`은 `submitted`.
- 가상 문서: 제출 기한은 담당자가 공지한 날짜를 따른다는 규정.

이 내용은 실습 설명을 위한 **합성 사례**다. 실제 사용자의 과제·학교 데이터가 아니다.

## B-1. ① 사용자가 질문을 보낸다

- **누가:** 사용자와 프론트엔드.
- **입력:** 과제 제출 규정과 내 과제 상태에 대한 질문.
- **동작:** 프론트엔드가 질문을 HTTP 요청으로 FastAPI에 전송한다.
- **다음 전달:** FastAPI 서버.

이 단계에서는 아직 Agent도 RAG도 실행되지 않았다.

## B-2. ② FastAPI가 HTTP 요청을 접수한다

- **누가:** FastAPI.
- **입력:** 사용자의 질문이 담긴 요청.
- **동작:** 해당 API 경로의 요청 처리로 연결한다.
- **다음 전달:** 요청 검증과 사용자 인증 단계.

강의에서 보여 준 최종 API 예시는 `/api/v1/agent/ask`이지만, 이 연결은 **다음 개인 프로젝트를 위한 구현 골격**으로 제시되었다.

## B-3. ③ Pydantic이 질문 형식을 검사한다

- **누가:** FastAPI의 요청 검증 과정에서 사용하는 Pydantic.
- **입력:** 질문 문자열과 정의한 요청 필드.
- **동작:** 질문이 비어 있지 않은지, 허용 길이를 넘지 않는지 등 Schema 조건을 검사한다.
- **결과:** 잘못된 입력이면 다음 단계를 진행하지 않고 요청 오류를 반환한다.

**구분:** Pydantic은 입력이 **형식상 올바른지** 확인한다. 로그인한 사람에게 어떤 데이터 조회 권한이 있는지까지 대신 판단하지 않는다.

## B-4. ④ FastAPI가 사용자를 인증한다 (Authentication)

- **누가:** 서버의 로그인·세션·토큰 인증 기능.
- **입력:** 서버가 검증할 수 있는 인증 정보.
- **동작:** 실제 로그인 사용자가 누구인지 확인한다.
- **결과:** 신뢰할 수 있는 서버 측 `user_id`를 확보한다.

예시에서는 서버가 확인한 사용자가 `stu-001`이다.

**매우 중요:** 사용자가 질문 글에 `user_id=stu-002`라고 적었다고 해서 이를 인증 신원으로 사용하면 안 된다. **신원은 모델이 만드는 값이 아니라 서버가 인증한 값**이다.

인증에 실패했다면 Agent 실행을 시작하기 전에 거절한다.

## B-5. ⑤ 서버가 Agent 실행을 요청한다

- **누가:** FastAPI에 등록된 서비스 처리 코드.
- **입력:** 검증된 사용자 질문 + 서버가 인증한 사용자 정보.
- **동작:** `create_agent`로 준비해 둔 Agent 실행 객체를 호출한다.
- **다음 전달:** Agent Harness와 Chat Model.

이때 질문은 `HumanMessage`로 들어가고, 서버가 확인한 사용자의 신원은 **별도의 Runtime Context**로 전달한다.

**핵심:** 질문 메시지와 신뢰된 신원은 같은 것이 아니다.

## B-6. ⑥ Harness가 모델에게 사용 가능한 Tool 설명을 전달한다

- **누가:** Agent Harness.
- **입력:** 사용자 질문, 대화 메시지, 사전에 등록된 Tool의 이름·설명·입력 규칙.
- **동작:** 모델이 어떤 Tool을 쓸 수 있는지 알 수 있게 구성한 뒤 모델을 호출한다.
- **사용 가능한 Tool:** `rag_search`, `lookup_status`.

`bind_tools()`는 Tool 목록의 Schema를 모델에 제공하는 구성 방식이고 **그 자체로 Tool을 실제 실행하지 않는다.**

## B-7. ⑦ LLM이 질문을 보고 다음 행동을 제안한다

- **누가:** Tool Calling을 지원하는 LLM.
- **입력:** 사용자 질문 + 이전 메시지 + Tool 설명.
- **동작:** 필요한 도구가 있는지, 있다면 어떤 도구에 어떤 인수를 전달할지 판단해 응답한다.
- **출력:** `tool_calls`가 포함된 `AIMessage` 또는 최종 답변 `AIMessage`.

예시의 질문에는 **규정 정보**와 **현재 제출 상태**가 모두 필요하므로, 모델이 두 Tool을 제안하는 경우를 설명하겠다.

하지만 실제 모델은 Tool을 0개, 1개 또는 여러 개 선택할 수 있다. **항상 두 개를 호출한다고 단정하면 안 된다.**

## B-8. ⑧ 모델이 구조화된 Tool Call 요청을 만든다

Tool Call은 “이 함수를 실제 실행해 달라”는 **제안서**에 가깝다.

예시:

| 요청 번호 | Tool 이름 | 모델이 제안한 입력 | 무엇을 알아보려는가 |
|---|---|---|---|
| call_001 | `rag_search` | 과제 제출 규정 / 학사 | 문서에 적힌 규정 |
| call_002 | `lookup_status` | 과제 ID 101 | 나의 현재 제출 상태 |

하나의 Tool Call에는 대표적으로 다음 정보가 있다.

- **`name`:** 실행을 요청한 Tool 이름.
- **`args`:** Tool에 전달할 입력 인수.
- **`id`:** 나중에 실행 결과를 이 요청과 짝짓기 위한 고유한 호출 ID.

여기서 `lookup_status`의 모델 인수는 `task_id=101`이며 **인증된 `user_id`는 모델 인수에 넣지 않는다.**

## B-9. ⑨ Harness가 Tool 요청을 검증한다

- **누가:** Agent Harness의 Dispatcher와 Tool 입력 검증 코드.
- **입력:** 모델이 제안한 `name`, `args`, `id`.
- **동작:** 등록된 Tool인지, 입력 형식이 유효한지, 호출 상한을 넘지 않는지 확인한다.
- **결과:** 검사를 통과한 Tool만 실제 실행한다.

예를 들어 모델이 등록하지 않은 Tool 이름을 요구하면 실행하지 않는다.

또한 `task_id=-1`이라면 양의 정수 규칙에 맞지 않으므로 **DB 조회 전에** 막을 수 있다.

**중요:** 입력 검사를 통과했더라도 **타인 데이터 접근 권한**까지 얻은 것은 아니다. 권한 검사는 조회 전에 별도로 필요하다.

## B-10. ⑩ `rag_search` Tool이 실행된다 — 규정 확인 경로

- **누가:** 서버에 등록된 `rag_search` Python Tool.
- **입력:** 과제 제출 규정이라는 검색 질문과 허용된 Category.
- **동작:** 기존 Day27 Enhanced RAG 서비스에 질문을 넘긴다.
- **다음 전달:** 기존 RAG 검색·생성 단계.

**Day29에서 RAG를 새로 만드는 것이 아니다.** 이전에 만든 RAG 기능을 Tool의 형태로 감싸서 **필요할 때만 호출**할 수 있게 한다.

## B-11. ⑪ RAG 내부에서 E5가 질문 벡터를 만든다

- **누가:** 기존 RAG의 Embedding 처리와 E5 모델.
- **입력:** 과제 규정 검색 질문.
- **동작:** 질문을 E5-small이 사용하는 384차원 벡터로 변환한다.
- **결과:** DB에서 관련 문서를 검색할 질문 벡터.

이 단계는 **질문에 대한 새 Embedding**이다. 저장된 모든 원본 문서를 매 요청마다 다시 Parsing·Chunking·Embedding하는 것이 아니다.

## B-12. ⑫ PostgreSQL + pgvector가 관련 문서 후보를 검색한다

- **누가:** 기존 RAG의 DB 검색 코드와 PostgreSQL·pgvector.
- **입력:** 질문 벡터와 문서 검색 조건.
- **동작:** 현재 공개된 유효 문서 중 벡터 거리가 가까운 Chunk 후보를 찾는다.
- **출력:** Chunk 본문과 출처 Metadata가 있는 검색 후보.

**참고:** Category 허용 목록만으로 문서 접근 권한이 자동 보장되지는 않는다. 실제 서비스에서는 인증된 사용자에게 보여 줘도 되는 문서인지 별도로 제한해야 한다.

## B-13. ⑬ Cross-Encoder Reranker가 후보를 다시 정렬한다

- **누가:** 기존 Day27 RAG의 Cross-Encoder.
- **입력:** 검색 질문 + 이미 찾은 후보 문서.
- **동작:** 질문과 후보 문서 쌍의 관련성 점수를 계산해 순서를 재조정한다.
- **출력:** 재정렬된 후보 목록.

Reranker는 **기존에 검색되지 않은 문서를 새로 만들어 추가하지 못한다.**

강의 환경의 RAG는 E5와 Cross-Encoder에 CUDA GPU를 사용하도록 제시되어 있다.

## B-14. ⑭ RAG의 Context Builder가 실제 근거를 선택한다

- **누가:** 기존 RAG 서비스의 Context 선택 단계.
- **입력:** 재정렬된 Document 후보.
- **동작:** 후보 수, 길이 예산, 중복 여부 등을 확인해 이번 답변에 제공할 문서를 고른다.
- **출력:** LLM이 읽을 Context와 실제 포함한 문서의 출처 기록.

**검색된 모든 후보의 ID가 최종 인용 허용 ID가 되는 것은 아니다.** 실제 Context에 포함한 문서의 ID만 검증 기준으로 사용한다.

## B-15. ⑮ RAG 내부 LLM이 규정을 바탕으로 답변을 생성한다

- **누가:** 기존 RAG의 Prompt·Chat Model.
- **입력:** 규칙 + 규정 관련 질문 + 선택된 Context.
- **동작:** 검색 문서에 근거한 답변을 생성한다.
- **출력:** 답변·상태·출처 후보.

강의의 기본 `rag_search` 설계는 **Answer Tool**이다. RAG 내부에서 LLM 답변 생성까지 수행하므로, 이 답변이 Agent에게 다시 전달되고 Agent LLM이 최종 답을 구성할 수 있다.

따라서 Agent의 LLM과 RAG 내부 LLM 호출이 모두 발생하면 **이중 생성 비용**이 생길 수 있다.

## B-16. ⑯ RAG Tool이 출처와 상태를 검증한 결과를 반환한다

- **누가:** 기존 RAG의 Validator와 `rag_search` Tool Wrapper.
- **입력:** RAG 답변과 실제 포함된 문서의 출처 정보.
- **동작:** 근거가 있는 답변, 근거 부족, 실행 오류를 구분하고 출처를 검증한다.
- **출력:** 예를 들어 `status=answered`, `answer`, `sources`로 구성된 Tool 결과.

문서에 필요한 날짜가 없다면 `insufficient_context`가 될 수 있다. 반면 DB 연결 실패, GPU 오류 등은 **정보 부족이 아니라 실행 오류**다.

**주의:** 출처 ID가 실제 Context에 포함됐는지 검사하는 것과, 답변 내용의 모든 주장이 원문에 의해 지지되는지를 확인하는 **Faithfulness/Grounding 검사**는 다른 문제다.

## B-17. ⑰ `lookup_status` Tool은 인증된 사용자 범위에서 DB를 조회한다

- **누가:** 등록된 `lookup_status` Python Tool, 서버 권한 검사, PostgreSQL.
- **입력:** 모델이 제안한 과제 ID 101 + **서버가 전달한** 인증 사용자 `stu-001`.
- **동작:** 과제 ID가 올바른지 검사하고, 조회 권한을 사용자 신원과 함께 확인한 뒤 **읽기 전용 SELECT**를 실행한다.
- **출력:** 사용자의 현재 제출 상태 또는 명시적인 미조회·권한·DB 오류.

개념적으로 DB는 다음 두 조건을 **함께** 만족하는 행만 조회한다.

- 과제 ID가 요청한 `101`과 일치할 것.
- 해당 행의 소유자 `owner_id`가 인증된 `stu-001`과 일치할 것.

조건을 만족하는 교육용 행이 있다면 `submitted` 상태를 반환한다.

**핵심:** LLM이 직접 SQL을 작성하거나 PostgreSQL에 접속하는 게 아니라 **개발자가 미리 정의한 제한된 조회 코드**를 Tool이 실행한다.

## B-18. ⑱ 각 Tool 실행 결과가 `ToolMessage`가 된다

- **누가:** Agent Harness.
- **입력:** RAG Tool 결과와 DB Tool 결과.
- **동작:** 각 결과를 해당 Tool Call ID와 연결해 대화 메시지 목록에 추가한다.
- **출력:** `ToolMessage`들.

예시:

| 모델이 낸 요청 | 서버가 확인한 결과 | 연결 기준 |
|---|---|---|
| `rag_search` — call_001 | “제출 기한은 담당자 공지 기준” + 출처 | `tool_call_id=call_001` |
| `lookup_status` — call_002 | 과제 101: `submitted` | `tool_call_id=call_002` |

`ToolMessage`는 **Tool이 실제로 실행된 뒤 반환한 결과**를 LLM에 전달하기 위한 메시지다.

이 예시에서는 두 Tool을 나란히 설명했지만, 실제로 둘을 한꺼번에 요청할지 하나씩 요청할지는 모델의 응답과 실행 설정에 따라 달라진다.

## B-19. ⑲ Harness가 Tool 결과를 포함해 LLM을 다시 호출한다

- **누가:** Agent Harness.
- **입력:** 최초 사용자 질문 + 이전 AIMessage의 Tool Call + 실제 ToolMessage.
- **동작:** 추가 정보를 받은 상태로 모델이 다음 행동을 선택하도록 다시 호출한다.
- **출력:** 새로운 `AIMessage`.

이 지점에서 **Agent Loop**가 만들어진다.

```text
LLM: 도구가 필요합니다
   ↓
Harness: 허용된 도구 실행
   ↓
ToolMessage: 실제 결과 반환
   ↓
LLM: 결과를 읽고 다시 판단
   ├─ 다른 도구 필요 → Harness로 다시 요청
   └─ 충분함 → 최종 답변
```

이것이 기존 **고정 RAG**와 가장 크게 다른 부분이다.

## B-20. ⑳ LLM이 최종 AIMessage를 작성한다

- **누가:** Agent의 Chat Model.
- **입력:** 사용자 질문, 실행된 Tool 결과, 시스템 응답 규칙.
- **동작:** 실제 확인된 규정과 현재 상태를 바탕으로 최종 자연어 답변을 구성한다.
- **출력:** Tool Call 요청이 없는 최종 `AIMessage`.

교육용 답변 예시:

> “과제 제출 기한은 담당자가 공지한 날짜를 따릅니다. 조회한 101번 과제는 제출 완료 상태입니다.”

**확인하지 못한 날짜를 임의로 만드는 것은 금지**다. 만약 DB 조회가 실패했다면 정상적으로 제출됐다고 단정하면 안 된다.

## B-21. ㉑ 서버가 Agent 실행 결과를 전달받는다

- **누가:** Agent 실행을 호출했던 FastAPI 서비스 코드.
- **입력:** Agent 실행 결과 State.
- **동작:** 누적된 `messages`에서 모델의 최종 응답과 Tool 결과를 확인한다.
- **출력:** 검증할 최종 답변 후보.

`agent.invoke()`의 반환값은 **단순한 답변 문자열이 아니라 `messages`를 담고 있는 State**이다. 실행 중 발생한 AIMessage·ToolMessage가 함께 있을 수 있다.

**최종 텍스트를 꺼내는 작업과 그 텍스트가 안전하고 정확한지 검사하는 작업은 별개**다.

## B-22. ㉒ 서버 Validator가 결과를 검사한다

- **누가:** 서버가 별도로 구현한 Validator.
- **입력:** 최종 AIMessage, 실제 실행된 Tool 기록, 서버가 검증한 출처, 인증된 신원과 오류 상태.
- **동작:** 허용된 도구만 사용됐는지, 조회 범위와 결과가 유효한지, 존재하지 않는 출처를 인용하지 않았는지 확인한다.
- **결과:** 검증된 결과 또는 명시적인 실패.

검사 예시:

- 실제 Tool 실행 없이 “확인했다”고 답하지 않았는가?
- RAG 출처가 실제 Context에 포함된 검증된 출처인가?
- 타인의 제출 상태가 노출되지 않았는가?
- DB 실패를 “미제출” 또는 “정보 부족”으로 바꾸지 않았는가?
- 한도를 초과한 반복이 발생하지 않았는가?

이 단계는 Agent가 자연어로 그럴듯한 답변을 했다는 이유만으로 생략하지 않는다.

## B-23. ㉓ FastAPI가 응답이나 오류를 반환한다

- **누가:** FastAPI 요청 처리 부분.
- **입력:** 서버 Validator의 검증 결과.
- **동작:** 정상이라면 답변과 검증된 출처를 HTTP 응답으로 구성하고, 실패라면 정책에 맞는 오류를 반환한다.
- **출력:** 프론트엔드가 받을 HTTP 응답.

강의의 **교육용 정책 예시**에서는 정상 200, DB 장애 503, 상위 모델 인증 오류 503 같은 상태 코드를 보여 준다. 이것은 프로젝트에서 확정해야 할 API 계약의 예시이지, 모든 구현에서 반드시 같은 코드가 자동 반환된다는 뜻은 아니다.

## B-24. ㉔ 프론트엔드가 사용자에게 결과를 보여 준다

- **누가:** 프론트엔드.
- **입력:** FastAPI의 HTTP 응답.
- **동작:** 정상 답변, 원문 출처, 확인하지 못한 정보 또는 서비스 오류를 사용자에게 표시한다.
- **결과:** 사용자 요청에 대한 한 번의 서비스 처리 종료.

여기까지가 **복합 질문에서 두 Tool이 실제로 필요하고 성공했을 때의 예시 흐름**이다. 아래에서 Tool이 0개·1개인 경우와 오류 흐름도 구분해 본다.

# PART C. 질문에 따라 어떤 길로 갈까? 네 가지 시나리오

## C-1. 시나리오 1 — 규정만 질문: RAG Tool 한 개

**질문:** “과제 제출 규정이 뭐야?”

1. FastAPI가 질문을 접수하고 사용자를 인증한다.
2. Harness가 Tool 설명과 함께 LLM을 호출한다.
3. LLM이 `rag_search`가 필요하다고 제안할 수 있다.
4. Harness가 입력·허용 Tool을 검사한 뒤 `rag_search`를 실행한다.
5. RAG는 관련 규정 검색 → 재정렬 → Context 선택 → 답변 생성·출처 검증을 수행한다.
6. 결과를 `ToolMessage`로 LLM에 전달한다.
7. LLM이 근거를 반영한 답변을 작성한다.
8. 서버가 최종 출처를 검증하고 사용자에게 반환한다.

**왜 DB Tool이 필요 없을까?** 질문이 개인의 현재 제출 상태가 아니라 **문서에 적힌 규정**을 묻기 때문이다.

## C-2. 시나리오 2 — 내 상태만 질문: DB Tool 한 개

**질문:** “내 101번 과제 제출됐어?”

1. 서버에서 로그인한 사용자 ID를 인증한다.
2. LLM이 `lookup_status`를 제안할 수 있다.
3. 서버가 `task_id=101`의 형식과 호출 가능 여부를 검사한다.
4. DB Tool이 인증된 사용자 ID와 과제 ID를 함께 사용해 조회한다.
5. 실제 데이터가 있다면 현재 상태와 갱신 시각 등을 Tool 결과로 반환한다.
6. Harness가 이를 LLM에 다시 전달한다.
7. LLM이 현재 상태를 설명하고 서버가 검증 후 응답한다.

**왜 RAG Tool이 필요 없을까?** 제출 여부는 **문서 규정이 아니라 DB에 기록된 현재 개인 상태**이기 때문이다.

## C-3. 시나리오 3 — 복합 질문: 두 Tool이 필요할 수 있음

**질문:** “제출 규정이랑 내 101번 상태 알려줘.”

- `rag_search`는 **일반 규정**을 확인한다.
- `lookup_status`는 **내 현재 상태**를 확인한다.
- Harness는 두 결과의 요청 ID를 구분해 모델에게 전달한다.
- LLM은 확인된 두 종류의 정보를 묶어 답변한다.

두 결과 중 하나가 실패했다면 **성공하지 않은 사실까지 답하지 않아야 한다.** 강의의 예시에서는 규정은 답하면서 “내 상태는 조회할 수 없다”고 구분하기도 한다.

## C-4. 시나리오 4 — 단순 인사: Tool이 필요 없을 수 있음

**질문:** “안녕하세요.”

- 모델은 Tool을 제안하지 않고 바로 최종 응답을 만들 수 있다.
- Harness는 Tool 실행이 없는 결과를 받아 종료한다.
- 서버는 여전히 필요한 응답 정책과 오류 처리를 적용한다.

**Tool Calling Agent라고 해서 매번 무조건 Tool을 호출하는 것은 아니다.**

## C-5. 시나리오 5 — 타인의 과제를 요청함

**질문:** “다른 학생의 202번 과제 상태 알려줘.”

- 모델이 실수로 `lookup_status(task_id=202)`를 제안할 수도 있다.
- 하지만 Tool은 현재 서버가 인증한 사용자의 `user_id`와 `owner_id`가 같은 행만 조회한다.
- 타인 데이터이면 결과를 공개하지 않는다.
- 예제에서는 `not_found_or_forbidden`처럼 **없음과 권한 밖을 외부에 구분해 노출하지 않는 정책**도 사용한다.

**모델의 도구 선택 자체가 조회 권한을 만들어 주지는 않는다.**

# PART D. 오늘 반드시 이해해야 할 기본 개념 16가지

## D-1. AI Agent는 무엇인가?

AI Agent는 **LLM이 현재 질문과 사용 가능한 Tool을 보고 다음 행동을 제안하고, 실행 환경이 그 행동을 수행한 뒤 결과를 다시 모델에 보여 주는 구조**다.

이전 Day26의 RAG에서는 개발자가 `검색 → Context → 생성`이라는 순서를 고정했다. Day29에서는 사용자 요청에 따라 LLM이 `rag_search`, `lookup_status` 또는 아무 Tool도 사용하지 않는 선택을 **제안**할 수 있다.

그러나 **모델에게 임의의 명령이나 DB 권한이 생기는 것은 아니다.** 서버가 미리 허용한 Tool만 실행한다.

## D-2. Model과 Harness의 역할은 왜 나누는가?

| 구성 | 실제 역할 | 하지 않는 일 |
|---|---|---|
| **LLM / Model** | 질문과 Tool 설명을 읽고 호출 요청 또는 최종 답변을 작성 | Python Tool을 직접 실행하거나 사용자 권한을 확정하지 않음 |
| **Agent Harness** | 모델 API 호출·Tool 요청 전달·실행·결과 재입력·반복 종료 관리 | 모델의 자연어 답변을 자동으로 참이라고 보증하지 않음 |
| **Tool** | 서버에 미리 구현된 검색·조회 등의 특정 작업을 실제 수행 | 모델이 요구했다고 무제한 접근을 허용하지 않음 |
| **Validator** | 출처·상태·권한·오류 계약을 검사 | 확인되지 않은 사실을 임의로 보충하지 않음 |

**기억할 말:** *Model은 선택을 제안하고, Harness가 실행을 관리한다.*

## D-3. Tool이란 무엇인가?

Tool은 Agent가 사용할 수 있도록 **이름, 목적, 입력 조건, 반환 형식**을 정해 둔 기능이다.

예를 들어 `lookup_status`는 “과제 ID를 받아, 인증된 사용자 자신의 현재 제출 상태를 읽는다”는 기능이다. 이것은 자연어 질문을 받는 LLM과 달리 특정 입력과 출력 규칙을 갖는다.

Tool을 잘 설계하려면 네 가지가 필요하다.

1. **Name:** Tool의 고유한 이름.
2. **Description:** 언제 사용해야 하고 어떤 역할을 하는지 설명.
3. **Args Schema:** 어떤 입력값을 어떤 자료형·범위로 받는지 규정.
4. **Output Contract:** 정상·정보 부족·권한 밖·오류를 어떤 형태로 반환하는지 규정.

Description이 불명확하면 모델이 잘못된 Tool을 고를 수 있다. 입력을 무제한 허용하면 잘못된 실행이나 보안 문제가 생길 수 있다.

## D-4. Tool Calling이란 무엇인가?

Tool Calling은 LLM이 일반 답변 문장 대신 **구조화된 도구 호출 요청**을 작성하는 기능이다.

- ‘도구를 실행해 달라’는 요청을 만드는 단계와,
- 서버가 실제 도구 함수를 실행하는 단계는 **서로 다르다**.

`bind_tools()`는 모델에 Tool의 사용 설명·입력 Schema를 알려 주는 단계이고, `tool_calls`는 모델이 실제로 만들어 반환한 호출 요청 목록이다.

**오해:** `bind_tools()`만 실행하면 SQL 조회가 일어나는가? **아니다.**

## D-5. Tool Call ID는 왜 필요한가?

질문 하나에서 도구가 여러 개 필요할 수 있다.

예를 들어 `rag_search`와 `lookup_status`를 함께 요청했다면, 어떤 결과가 어떤 요청에 대응하는지 구분해야 한다.

- 요청 `call_001` → 규정 검색 결과 `ToolMessage(call_001)`.
- 요청 `call_002` → DB 상태 조회 결과 `ToolMessage(call_002)`.

이처럼 **Tool Call ID는 호출 요청과 실제 실행 결과의 짝을 맞추는 식별자**다. 누락·중복되면 결과가 뒤섞일 수 있다.

## D-6. Agent Loop란 무엇인가?

Agent는 한 번 모델을 호출하고 끝날 수도 있지만, Tool 결과를 보고 **추가적인 모델 호출을 이어갈 수도 있다.**

```text
모델 판단
   ↓
Tool 호출 제안
   ↓
허용된 Tool 실행
   ↓
Tool 결과 전달
   ↓
모델 재판단
   ├─ 더 필요한 Tool이 있음 → 다시 실행
   └─ 충분함 → 최종 답변으로 종료
```

이 반복을 **Agent Loop**라고 한다. 종료되는 이유는 모델이 최종 답변을 내놓거나, 서버의 실행 정책이 중단하도록 결정했기 때문일 수 있다.

**강의 주의:** Tool 호출 횟수를 제한하더라도 모델 호출 횟수, 전체 실행시간, HTTP Timeout까지 자동으로 제한되는 것은 아니다.

## D-7. `create_agent`는 무엇을 해 주는가?

LangChain의 `create_agent`는 미리 준비한 Chat Model, Tool 목록, 시스템 지시, Runtime Context, 실행 한도 등을 연결해 **Agent를 실행할 수 있는 구조**를 만든다.

실제 사용자가 질문하면 Harness가 다음을 관리한다.

- 모델에게 메시지 전달.
- 모델의 Tool 요청 감지.
- 허용된 Tool 실행.
- 실행 결과를 ToolMessage로 재전달.
- 모델을 다시 호출하거나 종료.

그러나 **권한 검사·출처의 진실성·DB 보안·업무 규칙이 자동으로 완성되는 것은 아니다.**

## D-8. 메시지 네 종류는 어떻게 다른가?

| 메시지 | 누가 만드는가 | 역할 | 쉬운 비유 |
|---|---|---|---|
| `SystemMessage` | 개발자·서비스 설정 | 모델의 기본 역할·규칙 전달 | 업무 지침서 |
| `HumanMessage` | 사용자 | 이번에 해 달라는 요청 | 고객 요청서 |
| `AIMessage` | LLM | Tool 요청 또는 최종 답변 | 담당자의 작업 제안·회신 |
| `ToolMessage` | 실행 환경 | 실제 Tool 실행 결과를 모델에 전달 | 현장에서 확인한 결과 보고서 |

**중요:** `AIMessage`에 Tool 호출 요청이 있다고 해서 Tool 실행까지 완료된 것은 아니다. 해당 `ToolMessage`와 서버 실행 기록이 있어야 수행 여부를 확인할 수 있다.

## D-9. RAG Tool과 DB Tool은 왜 둘 다 필요할까?

**`rag_search`:** 문서에 적힌 정책·규정·설명서를 검색한다.

**`lookup_status`:** 지금 DB에 기록된 개인의 제출 상태처럼 구조화된 현재 정보를 조회한다.

예를 들어 “과제 마감 규정은?”과 “내 과제가 제출됐어?”는 다른 질문이다.

- 규정을 찾아도 개인 제출 여부는 알 수 없다.
- 개인 제출 상태를 조회해도 모든 제출 규정이 나오는 것은 아니다.

둘을 모두 묻는 요청은 두 출처의 결과를 합쳐야 할 수 있다.

## D-10. Answer Tool과 Evidence Tool의 차이는 무엇인가?

| 구분 | RAG Answer Tool | RAG Evidence Tool |
|---|---|---|
| 내부 기능 | 문서 검색 → 근거 선택 → RAG 내부 LLM으로 답변 생성 | 문서 검색 → 근거 선택까지만 수행 |
| Tool 출력 | `answer` + `sources` + `status` | 선택한 Context/근거 + 출처 |
| 최종 답변 | Agent LLM이 RAG 답변을 읽고 다시 구성할 수 있음 | Agent LLM이 근거를 읽고 최종 생성 |
| 장점 | 기존 Day27 RAG 전체를 쉽게 재사용 | 답변 생성 단계를 한곳에 집중시킬 수 있음 |
| 주의점 | **RAG LLM + Agent LLM 이중 생성 비용** 가능 | 근거·출처 전달 계약을 더 신중히 설계해야 함 |

이번 강의의 구현 목표는 **Answer Tool을 먼저 사용**하는 것이다. Evidence Tool은 대안으로 비교한다.

## D-11. Tool Schema 검증과 권한 검증은 무엇이 다른가?

다음 두 문장을 비교하자.

- “과제 ID가 `101`이라는 양의 정수인가?” → **Schema 검증**.
- “현재 로그인 사용자가 101번 과제를 조회해도 되는가?” → **Authorization(권한 검사)**.

`101`이 양의 정수여도 타인 데이터일 수 있다. **자료형 검사 성공 ≠ 조회 권한 승인**이다.

## D-12. Authentication과 Authorization은 어디에서 실행될까?

| 용어 | 의미 | 강의 구조에서 실행 위치 |
|---|---|---|
| **Authentication(인증)** | “로그인한 사람이 누구인가?” | FastAPI에서 Agent를 실행하기 전에 확인 |
| **Authorization(인가·권한 검사)** | “이 사람이 이 자료를 볼 수 있는가?” | Tool·DB가 실제 조회를 실행하기 전에 확인 |

예를 들어 사용자가 로그인에는 성공했어도 **다른 학생의 제출 상태를 읽을 권한**까지 얻은 것은 아니다.

**신뢰 경계:** 인증된 `user_id`는 서버가 별도로 전달하고, 모델이 지어낸 `user_id`나 사용자 메시지의 임의 ID를 믿지 않는다.

## D-13. 왜 DB Tool을 Read-only로 만들까?

이번 강의의 DB Tool은 제출 상태를 **읽는 역할만** 한다.

- 미리 작성한 SELECT SQL만 사용한다.
- 조회 인수를 SQL 문장과 분리해서 전달한다(Parameterized SQL).
- `task_id`와 인증된 사용자의 `owner_id`를 함께 조건으로 검사한다.
- DB 계정도 가능하면 SELECT만 가능한 전용 계정으로 제한한다.

이는 **최소 권한 원칙**에 해당한다. 상태를 확인하는 질문에 수정·삭제 권한까지 줄 이유가 없다.

Parameterized SQL의 `%s`는 **입력값을 별도로 바인딩할 자리**라는 뜻이다. 사용자 입력을 SQL 문자열에 그대로 이어 붙이는 방식보다 안전하게 다루도록 돕는다.

## D-14. 결과가 없을 때 무엇을 구분해야 할까?

“확인하지 못했다”는 상황에도 이유가 여러 가지 있다.

| 상황 | 의미 | 올바른 방향 |
|---|---|---|
| RAG의 `insufficient_context` | 문서 검색은 정상적이었지만 답할 근거가 부족 | 추측하지 않고 정보 부족 안내 |
| DB의 `not_found` | 허용된 조회 범위에서 해당 데이터가 없음 | 존재하지 않음을 정책에 맞게 표시 |
| DB의 `not_found_or_forbidden` | 외부에 미존재와 권한 밖을 구별해 공개하지 않음 | 타인 정보 노출 없이 조회 불가 안내 |
| `validation_error` | Tool 입력이 Schema에 맞지 않음 | 실제 실행 전에 거절 |
| `db_error` | DB 접속이나 조회 자체가 실패 | 시스템 오류로 분리 |
| `model_auth_error` | 모델 API 인증·설정 오류 | 요청 중단·운영 오류로 처리 |
| `limit_exceeded` | Tool 호출 상한을 넘음 | 반복 중단·기록 |

**절대로 해서는 안 되는 해석:** DB가 꺼져 있는데 “과제를 제출하지 않았습니다”라고 말하거나, 모델 API 401을 “관련 문서가 없습니다”로 바꾸는 것.

## D-15. Fail closed란 무엇인가?

**검증에 실패하거나 안전 여부를 확인하지 못하면, 정상 성공으로 취급하지 않는 원칙**이다.

예시:

- 출처 ID가 실제 제공 문서에 없다 → 정상 답변으로 승인하지 않는다.
- DB 접속 실패 → “제출 안 됨”이라고 단정하지 않는다.
- Tool 이름이 허용 목록에 없다 → 실행하지 않는다.
- 인증된 사용자 정보가 없다 → 개인 DB 조회를 진행하지 않는다.

Fail closed는 “모든 실패를 같은 오류로 표시하라”는 뜻이 아니다. **실패 종류를 구별하고, 허용되지 않은 성공을 만들지 않는 것**이다.

## D-16. Trace와 Audit Log는 왜 나눌까?

| 구분 | Trace | Audit Log |
|---|---|---|
| 목적 | 기술적으로 어떤 순서로 실행됐는지 재현 | 누가 어떤 접근을 요청했고 어떤 판정을 받았는지 기록 |
| 주로 기록 | 모델 요청, Tool Call, ToolMessage, 단계별 시간·오류 | 익명화된 사용자 ID, Tool 이름, 권한 허용/거절, 요청 식별자 |
| 주 사용처 | 개발·디버깅·품질 평가 | 보안·운영·접근 조사 |

로그인이 성공했는지, 어떤 Tool을 실제로 실행했는지 확인할 수 있어야 하지만 **API Key·로그인 토큰·개인정보·민감 문서 원문을 무분별하게 남겨서는 안 된다.**

# PART E. 비교해서 외우면 쉬운 개념 차이

| 헷갈리는 두 개념 | 무엇이 다른가? | 기억하기 |
|---|---|---|
| **고정 RAG vs Agent** | 고정 RAG는 정해진 검색→생성 순서, Agent는 Tool 사용 여부를 모델이 제안 | 고정 절차 vs 동적 제안 |
| **Rule-based Workflow vs Agent** | 개발자가 만든 if/else가 분기 vs 모델이 다음 행동 제안 | 규칙 분기 vs 모델 제안 |
| **LLM vs Harness** | 모델은 Tool 요청·답변 작성, Harness는 실행·반복·결과 전달 관리 | 제안자 vs 실행 관리자 |
| **`bind_tools` vs Tool 실행** | Tool 설명 전달 vs Python 함수 실제 호출 | 도구 소개 vs 도구 사용 |
| **Tool Call vs ToolMessage** | 실행 요청 vs 실제 실행 결과 | 작업 지시 vs 결과 보고 |
| **AIMessage vs ToolMessage** | 모델 응답 vs Tool 실행 환경의 응답 | 모델 말 vs Tool 결과 |
| **Name vs Description** | Tool 고유 이름 vs 모델이 사용 시점을 판단할 설명 | 이름 vs 기능 설명 |
| **Args Schema vs Output Contract** | 입력 규칙 vs 반환 상태·필드 약속 | 들어오는 값 vs 나가는 값 |
| **Schema vs Authorization** | 값의 형식 검사 vs 사용자 권한 검사 | 유효한 ID vs 볼 수 있는 ID |
| **Authentication vs Authorization** | 누구인지 확인 vs 무엇에 접근 가능한지 확인 | 신원 vs 권한 |
| **Tool args vs Runtime Context** | 모델이 제안할 입력 vs 서버가 인증해 전달한 신뢰된 정보 | 과제 ID vs 로그인 사용자 ID |
| **RAG vs DB Tool** | 문서 규정 vs 현재 개인 상태 | 문서 지식 vs 운영 상태 |
| **Answer Tool vs Evidence Tool** | RAG가 답변까지 생성 vs RAG가 근거만 반환 | 답변 포함 vs 근거만 |
| **Citation ID vs Tool Call ID** | 답변의 문서 출처 ID vs 도구 요청·결과 연결 ID | 어디서 찾았나 vs 어떤 호출 결과인가 |
| **Context 출처 vs 모델이 적은 출처** | 실제 LLM에게 제공한 근거 vs 모델이 주장하는 출처 | 서버 기록이 검증 기준 |
| **No-answer vs DB 오류** | 확인했지만 근거 없음 vs 확인 자체가 실패 | 정보 부족 vs 실행 실패 |
| **Not Found vs Forbidden** | 데이터가 없음 vs 해당 사용자의 접근 권한 없음 | 미존재 vs 권한 밖 |
| **Trace vs Audit** | 실행 디버깅 vs 접근 감사 | 동작 기록 vs 권한 기록 |
| **Tool 호출 제한 vs Timeout** | 실행 가능한 Tool 호출 횟수 vs 전체 대기·실행 시간 | 횟수 vs 시간 |
| **Agent 결과 State vs 최종 답변 문자열** | 모든 메시지·결과를 담은 상태 vs 화면에 보여 줄 텍스트 | 실행 전체 vs 표시할 문장 |
| **Gold Label vs Tool 입력** | 평가할 때만 쓰는 정답 기준 vs 실제 서비스를 실행하는 인수 | 채점용 답안을 서비스에 넣지 말기 |
| **시뮬레이션 Fixture vs 실측 Trace** | 미리 만들어 둔 가상 실행 결과 vs 실제 API/DB가 실행된 기록 | 학습 예시 vs 실제 측정 |

## F-2. ‘원본 질문’, ‘Tool 인수’, ‘서버 신원’을 한데 섞지 않기

- **원본 질문:** “과제 제출 규정과 내 101번 과제 상태 알려줘.”
- **RAG Tool 입력:** “과제 제출 규정”, Category “학사”.
- **DB Tool 입력:** 과제 ID 101.
- **서버 Runtime Context:** 인증된 사용자 ID `stu-001`.
- **RAG Tool 반환:** 규정 답변과 검증된 출처.
- **DB Tool 반환:** 인증된 사용자의 과제 101 상태.
- **최종 Agent 답변:** 두 Tool 결과를 사용자 질문에 맞게 합친 자연어 설명.

**주의:** 모델이 문서에 없는 날짜나 사용자 신원을 만들어 냈다면 실제 확인 결과로 승인하지 않는다.

## F-3. 교육용 DB 데이터 사례

| 과제 ID | 소유자 ID | 제출 상태 | 수정 시각 |
|---|---|---|---|
| 101 | stu-001 | submitted | 2026-11-26 09:05 |
| 102 | stu-001 | pending | 2026-11-26 10:20 |
| 202 | stu-002 | submitted | 2026-11-25 17:30 |

예를 들어 서버에서 `stu-001`로 인증된 요청을 처리하고 있다면 `task_id=101`은 본인 상태를 확인할 수 있지만 `task_id=202`는 다른 소유자의 데이터이므로 공개하지 않는다.

이 값들은 **강의의 합성 데이터**다.

## F-4. 실제 응답에 나타날 수 있는 상태

```text
Agent의 Tool 실행 및 검증
        │
        ├─ RAG 정상: answered (+ verified sources)
        ├─ RAG 근거 부족: insufficient_context
        ├─ DB 정상 조회: ok (+ submission_status)
        ├─ DB 미조회/권한 밖: not_found_or_forbidden
        ├─ 입력 오류: validation_error
        ├─ DB·모델 오류: db_error / model_auth_error 등
        └─ 반복 상한 초과: limit_exceeded
```

여기 표시한 것은 **서로 다른 Tool과 단계에서 쓰는 상태들의 예시 모음**이다. 모든 값이 하나의 공통 `status` 필드에 동시에 들어간다는 뜻이 아니다.

# PART G. 주제별 용어 사전 — 처음 공부하는 사람을 위한 설명

## G-1. AI Agent와 실행 구조

| 용어 | 쉽게 설명하면 | 이번 수업에서의 역할 |
|---|---|---|
| **AI Agent** | LLM의 행동 제안과 서버의 도구 실행을 연결한 시스템 | RAG/DB 중 필요한 기능 선택 가능 |

| **Chat Model** | 역할이 구분된 메시지를 받아 모델 응답을 돌려주는 인터페이스 | Tool Calling 지원 모델 사용 |
| **Agent Harness** | 모델 호출과 Tool 실행·재호출을 운영하는 실행 환경 | 허용 Tool 실행·메시지 흐름 관리 |
| **Agent Loop** | Tool 결과를 받은 뒤 모델이 다시 판단할 수 있는 반복 | 요청 → Tool 결과 → 재판단 |
| **Workflow** | 미리 정한 순서나 규칙으로 실행하는 작업 흐름 | Agent와 비교하는 기준 |
| **Rule-based Workflow** | if/else 등 개발자가 작성한 규칙으로 분기하는 구조 | 모델 선택이 아닌 규칙 선택 |
| **Fixed RAG** | 검색과 생성 순서를 개발자가 고정한 RAG | Day26 기본 구조 |
| **Tool Calling** | 모델이 Tool 실행 요청을 구조화해 반환하는 기능 | 모델의 다음 행동 제안 |
| **`create_agent`** | Model·Tools 등을 묶어 Agent 실행 구조를 만드는 LangChain 함수 | 호출·재호출 루프 준비 |
| **`agent.invoke()`** | 준비된 Agent를 실제 실행하는 호출 | 메시지 State 반환 |
| **`bind_tools()`** | 모델에게 Tool 설명과 입력 Schema를 알려 주는 설정 | Tool 자체를 실행하지 않음 |
| **Tool Dispatcher** | 모델의 도구 요청을 허용된 실제 함수에 연결·실행하는 부분 | 허용 목록 기반 실행 |
| **Allowlist** | 서버가 실행을 허용한 이름의 목록 | 등록하지 않은 도구 실행 차단 |
| **Middleware** | 실행 과정 중간에 공통 검사·제한을 적용하는 구성 | 호출 횟수 제한 등 |
| **`ToolCallLimitMiddleware`** | 한 실행에서 Tool 호출 횟수에 상한을 주는 미들웨어 | 무한·과도한 호출 방지 |
| **Run Limit** | 정해 둔 Tool 호출 최대 횟수 | 교육용 예시 전체 4회 등 |
| **Loop Limit** | 반복 실행이 설정된 한도를 넘은 상태 | 중단·기록 필요 |
| **State** | Agent 실행 중 누적되는 현재 상태·메시지 정보 | `messages` 등 보관 |
| **`messages`** | 순서대로 쌓인 사용자·모델·도구 메시지 목록 | 실제 실행 흐름 확인 |

## G-3. Tool의 설계와 자료형 검사

| 용어 | 쉽게 설명하면 | 이번 수업 예시 |

| **Validation** | 데이터가 정의한 규칙을 만족하는지 검사 | 입력·출력 검사 |
| **Validation Error** | Schema·입력 제약을 어긴 경우 | 음수·문자열 과제 ID |
| **Adapter** | 기존 기능의 입출력을 새 인터페이스에 연결하는 코드 | 기존 RAG → Tool Wrapper |

## H-1. 잘못된 입력과 권한 문제

| 상황 | 발견하는 단계 | 왜 중단하거나 거절하는가? |
|---|---|---|
| 질문이 비어 있음 | FastAPI/Pydantic | 유효한 요청이 아님 |
| `task_id=-1` | Tool Args Schema 검사 | 양의 정수 규칙을 위반 |
| 모델이 알 수 없는 Tool 요청 | Harness Dispatcher | 허용 목록에 없는 기능 |
| 로그인하지 않은 요청 | FastAPI 인증 | 신뢰할 수 있는 사용자 신원이 없음 |
| 다른 학생의 과제 조회 | Tool/DB 권한 검사 | `owner_id`가 인증 사용자와 다름 |
| 문서 Category가 허용값이어도 접근 권한 없음 | RAG 검색 권한 검사 | 분류 값과 실제 자료 접근 권한은 다름 |

## H-2. 정상적인 업무 결과와 기술 오류

| 결과 | 예시 | 구분해야 할 점 |
|---|---|---|
| 정상 RAG 답변 | 규정 문서를 찾아 답변·출처 반환 | 출처가 실제 포함 문서인지 확인 |
| 정상적인 RAG 정보 부족 | 정확한 마감 날짜가 문서에 없음 | `insufficient_context`, 날짜를 지어내지 않음 |
| 정상 DB 조회 | 101번 과제 `submitted` | 현재 인증 사용자 본인 데이터일 것 |
| 미존재 또는 권한 밖 | 999번이 없거나 타인의 202번 과제 | DB 장애와 동일시하지 않음 |
| DB 장애 | PostgreSQL 연결 실패 | `db_error`, 결과를 추정하지 않음 |
| Provider 인증 오류 | LLM API 인증 실패 | `model_auth_error`, 근거 부족이 아님 |
| GPU 오류 | Reranker가 CUDA 환경에서 실패 | `gpu_error`, 검색 실패와 분리 |
| Tool 호출 한도 초과 | 계속 Tool을 추가 요청 | `limit_exceeded`, 정책에 따라 중단 |
| 출처 검증 실패 | 제공하지 않은 출처 인용 | 정상 답변으로 반환하지 않음 |

## H-3. 도구 반복 폭주를 막는 방법

강의에서는 `ToolCallLimitMiddleware`로 한 번의 Agent 실행에서 Tool을 몇 번까지 요청할 수 있는지 제한한다.

교육용 예시:

- 전체 Tool 호출 최대 **4회**.
- 특정 `lookup_status` Tool은 최대 **2회**.

이 숫자는 **예시 설정**일 뿐 모든 Agent에 권장되는 만능 값이 아니다.

그리고 Tool 호출 횟수에 제한을 걸었다고 해서 다음이 자동으로 제한되는 것은 아니다.

- LLM API 호출 횟수.
- 전체 실행 시간.
- PostgreSQL 요청별 대기 시간.
- FastAPI HTTP Timeout.

서비스에서는 필요한 제한들을 **각각** 관리해야 한다.

## H-4. 오류를 왜 전부 ‘모름’이라고 말하면 안 될까?

사용자에게 “과제가 제출되지 않았습니다”라고 표시하려면 실제로 DB에서 그 상태를 확인해야 한다.

DB 연결이 실패한 상황에서는 제출 여부를 알 수 없다. 따라서 올바른 설명은 **‘조회에 실패해 현재 상태를 확인할 수 없습니다’**와 같은 표현이어야 한다.

이 차이는 단순히 친절한 메시지의 문제가 아니라 **실제 결과의 진실성과 서비스 신뢰성**에 관한 문제다.

## H-5. Day28 평가와 연결되는 디버깅 관점

Agent 서비스에서 답변이 틀렸다면 아래처럼 단계별로 확인할 수 있다.

1. **모델의 Tool 선택:** 규정인데 DB Tool만 선택한 것은 아닌가?
2. **Harness 실행:** 모델이 제안한 Tool이 실제로 실행됐는가?
3. **입력·권한:** 과제 ID와 인증 사용자 범위를 올바르게 확인했는가?
4. **RAG 검색:** 올바른 규정 문서를 검색했는가?
5. **Reranking/Context:** 찾은 정답 문서가 최종 근거에 포함됐는가?
6. **Generation:** 포함된 문서의 숫자·조건을 LLM이 잘못 해석하지 않았는가?
7. **Citation:** 실제 포함 문서만 출처로 반환했는가?
8. **API:** 정상 상태와 장애 상태를 정확히 분리했는가?

Day28의 Recall·MRR·Faithfulness 같은 RAG 평가를 그대로 활용하면서, Day29에서는 **Tool Selection·권한·호출 반복**이라는 점검 항목이 추가된다.

# PART K. 가장 짧은 핵심 암기 요약

```text
[사용자 요청]
      ↓
[FastAPI: 질문 검증 + 사용자 인증]
      ↓
[Agent Harness: 모델 실행]
      ↓
[LLM: 어떤 Tool이 필요한지 제안]
      ↓
[Harness: Tool 이름·입력·호출 한도 검증]
      ↓
┌───────────────────────┬────────────────────────┐
│ rag_search            │ lookup_status          │
│ 문서 규정              │ 내 현재 제출 상태       │
│ E5→pgvector→Reranker  │ 인증된 owner_id 조건    │
│ →Context→LLM→출처검증 │ PostgreSQL SELECT       │
└───────────────────────┴────────────────────────┘
      ↓
[ToolMessage: 실행 결과와 호출 ID 연결]
      ↓
[LLM: 추가 Tool 요청 또는 최종 AIMessage]
      ↓
[서버 Validator: 출처·권한·오류 검증]
      ↓
[FastAPI HTTP 응답 → 사용자]
```

**최종 결론**

> **Day29는 ‘RAG가 답을 만드는 과정’에 더해, ‘어떤 기능을 언제 사용할지 LLM이 제안하고 서버가 안전하게 실행하는 과정’을 배우는 수업이다.**

**기억할 단어 여섯 개:**

**Model = 제안 / Harness = 실행 관리 / Tool = 실제 작업 / ToolMessage = 실행 결과 / Runtime Context = 신뢰된 서버 정보 / Validator = 최종 승인 검사**
