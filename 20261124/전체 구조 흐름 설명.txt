1. 사용자가 FastAPI 서버에 질문을 보낸다.
	- 프론트엔드에서 서버의 API주소로 HTTP 요청을 질문과 함께 보낸다.
	- 질문이나 대화 기록, 검색 조건등이 함께 전달된다.

2. FastAPI가 요청을 받고 Pydantic이 입력을 검사한다.
	- 질문이 비어있는지의 여부, 검색 개수 등등을 검사하고 입력이 잘못 되었다면 HTTP 422 오류를 반환하고 정상이라면 요청을 처리한	다.
3. FastAPI의 요청 처리 함수가 RAG 서비스 함수를 호출한다.
	- FastAPI가 검색과 LLM 생성을 모두 직접 실행 하는 것이 아닌 FastAPI에 등록된 함수가 서비스 함수를 호출하는 구조
	- RAG 서비스가 검색부터 답변 생성과 검증까지 전체 실행 순서를 관리한다.

3-1. Query Rewrite를 통해 검색에 적합한 질문으로 정리한다.
	- 사용자의 질문과 이전 대화 기록을 확인하고 원본 질문을 보존하고 검색에 사용할 질문을 별도로 만든다.
	- 이 과정에서 대화 기록만으로 검색 대상을 확정할 수 없다면 임의로 추측하지 않고 확인이 필요하다고 처리

3-2. Query Expansion 및 Muti-query 로 검색 표현을 확장한다.
	- 검색용 질문과 관련된 용어를 보충하거나 비슷한 의미의 질문 여러개를 준비한다.
	- 검색 질문이 여러개 일시 모든 검색 결과에서 중복된 Chunk를 제거한다.
	- 질문이 이미 명확하다면 생략 가능한 단계다.

4. RAG 서비스 함수가 Retriever를 실행하여 문서 검색을 요청한다.

5. Retriever 내부 검색 함수는 E5임베딩 모델을 통해 사용자 질문을 384차원 벡터로 변환한다.

6. PostgreSQL과 pgvector에 저장된 문서 벡터와 질문 벡터를 비교하여 후보들을 검색한다.
	- 지정된 검색 범위에서 관련성 높은 문서 후보들을 검색
	- 실제 검색 결과들은 Hit 형태로 정리된다.

7. 검색결과(hit)들이 Retriever를 거쳐 RAG서비스로 반환되며, Document 형태로 정리된다.
	- 검색된 내용들과 함께 어떤 원본 파일에서 가져왔는지 출처와 문서 버전 및 출처 ID와 같은 부가정보(Metadata)들과 합친다.
	- 본문과 Metadata가 LangChain Document 형태로 변환되어 Retriever의 결과로 반환된다.

7-1. Reranker가 검색된 후보 문서의 순위를 다시 평가한다.
	- 이 과정에서는 Cross-Encoder등의 모델이 사용된다.
	- Cross-Encoder는 검색용 질문과 후보 문서를 하나의 쌍으로 하여 함께 읽고 비교하여 관련성 점수를 계산한다.
	- 관련성 점수가 높은 순서로 검색 결과가 재 정렬된다.
	- Reranker는 이미 검색된 후보의 순위만 변경할 수 있고, 검색되지 않은 문서를 새롭게 찾아오지는 못한다.

8. 검색된 결과 중에 실제 LLM에게 보낼 근거들을 Context Builder를 통해 선택한다.
	- 이때 문서의 최대 갯수 및 길이 제한, 중복 여부등을 확인한다.
	- 여기서 추려진 실제 보낼 근거들을 Context라고 한다.

9. Prompt에서 LLM에서 전달한 입력을 구성한다.
	- 규칙, 질문, Context를 조합하여 모델에게 전달할 입력을 준비한다.

10. Prompt 작업을 거쳐 생성된 입력이 LLM에게 전달되고 LLM은 입력을 토대로 답변을 생성한다.
	- 생서된 답변과 출처 ID는 다시 RAG 서비스의 검증 단계로 전달된다.

11. 답변 검증 단계에서 문제가 없는지 검토한다.
	- 검사에 실패하면 승인되지 않고 오류 처리 단계로 넘어간다.

12. Grounding으로 답변과 원문을 대조한다.
	- 답변의 내용과 실제 문서가 일치하는지 검토하는 과정이다.

13. 답변이 필요한 검증을 통과하면 RAG 서비스는 최종 답변과 출저 정보를 준비한다.
	- 준비한 결과는 FastAPI에게 넘어가고 해당 결과를 반환받은 FastAPI는 HTTP 응답으로 프론트엔드로 전달한다.

14. HTTP응답을 받은 프론트엔드 단에서 사용자에게 결과값을 보여준다.
