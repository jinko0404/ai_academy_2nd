| 두 번째 Ctrl+C·재실행 후 A·B·C 조회 | A/B 200, C 404, 최종 N+2 | A(id=5)·B(id=6) 조회 200, C(id=7) 조회 404, 최종 5개 | A·B 유지, C 삭제 상태 유지, next_id=8 |

422 전후 next_id: 요청 전 8 → 요청 후 8로 동일하다.
최종 목록 수와 기대한 N+2: 최종 5개이며, 시작 N=3에서 N+2=5와 일치한다.
재시작 사이 seed 복사·reset·파일 수동 편집을 하지 않았는가: 하지 않았으며, API 요청으로 변경한 상태를 서버 재실행 후 확인했다.

## 5. 설명과 한계
내가 고른 요청의 흐름: POST /api/knowledge 요청을 보내면 KnowledgeWrite가 title·content·category의 필수 여부, 자료형과 길이를 검증한다. 검증에 통과하면 main.py의 create_knowledge에서 LOCK을 잡고 read_data()로 현재 상태를 읽는다. payload.model_dump()로 만든 새 항목에 next_id를 ID로 지정하고, entries에 추가한 뒤 next_id를 1 증가시킨다. write_data(data)가 storage.py에서 JSON 파일을 저장하면 새 항목을 201 응답으로 반환한다. 입력 검증에 실패하면 422를 반환하며 저장은 실행하지 않는다.

형식 검증과 지식 내용의 사실성 확인이 다른 이유: 형식 검증은 필수 필드가 있는지, 문자열인지, 길이 제한을 지키는지 확인하는 것이다. 입력 내용이 실제로 맞는 설명인지까지 확인하지 않으므로 형식이 올바른 잘못된 지식도 저장될 수 있다.

RAG·Agent 플랫폼에서 이 API의 역할: 검색이나 답변 생성에 활용할 원본 지식을 등록·조회·수정·삭제하는 관리 기능을 맡을 수 있다. 현재 구현은 원본 지식 관리 단계이며, 문서 임베딩·벡터 검색·LLM 호출·Agent 실행 기능은 연결하지 않았다.

현재의 한계 (로컬·인증/권한·검색/생성): 로컬 서버와 JSON 파일을 사용하는 실습용 구조다. 로그인과 사용자별 접근 권한이 없으며, 기본필수에서는 전체·ID별 조회만 제공하고 키워드·의미 검색이나 AI 답변 생성은 구현하지 않았다. LOCK은 같은 프로세스의 요청만 보호하므로 여러 서버 프로세스에서 동시에 파일을 수정하는 운영 환경에는 별도의 저장소와 동시성 처리가 필요하다.
