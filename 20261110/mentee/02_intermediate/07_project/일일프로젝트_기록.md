## 4. 요청 → 예상 → 실제 → 파일 변화

| 요청·동작 | 예상 | 실제 결과 | 확인한 파일 변화 |
|---|---|---|---|
| POST A·B·C 및 목록·상세 조회 | 201·200, N+3개 | 등록 201, A=4·B=5·C=6 발급, 목록·상세 조회 200, 총 6개 | 임시 JSON에 3개 추가, next_id 4→7 |
| B PUT (세 필드 모두 전송) | 200, ID·개수·next_id 유지 | 200, id=5의 content를 Send all three fields; keep the ID로 수정 | 임시 JSON 본문 변경, ID=5·항목 수 6개·next_id=7 유지 |
| 첫 번째 Ctrl+C·재실행 후 B 조회 | 수정 본문 유지 | 자동화로 서버 프로세스 종료·재실행 후 B 조회 200, 수정 본문 유지 | 재실행 후 임시 JSON 저장 내용 유지 |
| content="" POST | 422, 목록과 next_id 불변 | 422, 입력 검증 오류 반환 | 요청 전후 임시 JSON 바이트 동일, 항목 수 6개·next_id=7 유지 |
| C DELETE 및 상세 조회 | 204·빈 본문, GET 404 | id=6 삭제 시 204·빈 본문, 상세 조회 404 | 임시 JSON의 id=6 삭제, 항목 수 6→5개, next_id=7 유지 |
| 두 번째 Ctrl+C·재실행 후 A·B·C 조회 | A/B 200, C 404, 최종 N+2 | 자동화로 두 번째 종료·재실행 후 A/B 조회 200, C 조회 404, 최종 5개 | A/B 유지, C 삭제 상태 유지, next_id=7 |
| A와 프로젝트 전 기존 지식 조회 | 원래 내용 그대로 | A(id=4)와 기존 id=1·2·3의 전체 내용이 시작 전과 일치 | 기존 항목과 A 변경 없음 |

422 전후 next_id: 요청 전 7 → 요청 후 7로 동일하다.
최종 목록 수와 기대한 N+2: 최종 목록은 5개이며 N=3에서 N+2=5와 일치한다. next_id는 7이다.
재시작 사이 seed 복사·reset·파일 수동 편집을 하지 않았는가: 검증 시작 전에만 작업 파일을 임시 경로로 복사했다. 이후 두 번의 재시작 사이에는 복사·reset·수동 편집 없이 같은 임시 JSON을 사용했다.

## 5. 설명과 한계
<!-- TODO P-05: 한 요청이 입력 검증·저장·응답으로 이어지는 위치를 자신의 말로 설명하세요. -->
내가 고른 요청의 흐름: POST /api/knowledge를 보내면 KnowledgeWrite가 필수 필드·자료형·문자열 길이를 검증한다. 통과하면 create_knowledge가 LOCK 안에서 read_data()로 현재 상태를 읽고, payload.model_dump()로 만든 항목에 next_id를 부여한다. entries에 항목을 추가하고 next_id를 증가시킨 뒤 write_data(data)로 저장하고 201과 생성 항목을 반환한다. category 목록 조회는 main.py에서 파일을 읽어 select_category에 entries와 category를 전달하고 계산된 목록을 응답한다.

형식 검증과 지식 내용의 사실성 확인이 다른 이유: 필수 필드와 길이를 지키는지 검증해도 내용이 사실이라는 의미는 아니다. 잘못된 설명도 형식이 맞으면 저장될 수 있어 내용의 사실성은 별도로 확인해야 한다.

RAG·Agent 플랫폼에서 이 API의 역할: 검색과 답변 생성에 사용할 원본 지식을 등록·조회·수정·삭제하는 관리 기능을 맡을 수 있다. 현재는 category 필터까지 제공하며 문서 임베딩·벡터 검색·LLM 호출·Agent 실행은 연결하지 않았다.

현재의 한계 (로컬·인증/권한·검색/생성): 로컬 서버와 JSON 파일 기반의 실습 구조이며 로그인·사용자별 권한·키워드 및 의미 검색·AI 답변 생성이 없다. category는 문자열의 정확한 일치로만 조회한다. LOCK은 같은 프로세스에서만 공유되므로 여러 worker가 같은 파일을 수정하는 환경에는 별도의 동시성 처리가 필요하다. 이번 결과는 임시 데이터와 자동 서버 재실행으로 검증했으며 실제 작업 파일을 이용한 수동 Postman 실습 결과는 아니다.

응용 선택: 최종 상태에서 GET /api/knowledge?category=api는 200과 ID 2·3·4·5 목록을 반환했다. category=unknown은 200과 []를 반환했다. 목록 필터의 일치 항목이 없는 것은 정상 검색 결과이므로 상세 ID 조회 실패의 404와 다르다.
