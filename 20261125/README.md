# A. 오늘 수업을 이해하는 가장 쉬운 출발점

## A-1. Day26 → Day27 → Day28은 무엇이 달라졌나?

| 날짜 | 배운 것 | 한 줄 설명 |
|---|---|---|
| **Day24 이전** | Parsing·Chunking·Embedding·Indexing | 문서를 검색할 수 있도록 미리 준비했다. |
| **Day26** | Basic RAG·LangChain | 질문에 맞는 문서를 검색해 LLM이 답변하도록 연결했다. |
| **Day27** | Query Rewrite·Multi-query·Cross-Encoder Reranking | 검색할 질문을 개선하고, 검색된 후보의 순서를 더 정밀하게 조정했다. |
| **Day28 (오늘)** | **RAG Evaluation·Debugging** | **기존 RAG가 잘 작동하는지 시험하고, 문제의 원인이 어느 단계인지 찾는다.** |

오늘은 **RAG를 처음부터 다시 만드는 수업이 아니다.** 전날 만든 Enhanced RAG를 **평가 대상(Target)**으로 사용한다.

### 기억할 문장

> **Day26은 “답변을 만드는 방법”, Day27은 “검색을 개선하는 방법”, Day28은 “정말 개선됐는지 확인하고 무엇을 고칠지 판단하는 방법”이다.**

## A-2. 전체적으로는 서로 다른 두 흐름이 있다

**① 실제 사용자의 질문을 처리하는 RAG 흐름**

```text
사용자 질문
  ↓
FastAPI: 요청 수신·검사
  ↓
Query Rewrite: 필요한 경우 대화 맥락으로 검색 질문 정리
  ↓
Retriever: E5 질문 벡터 → PostgreSQL + pgvector 검색
  ↓
Reranker: Cross-Encoder로 검색 후보 재정렬
  ↓
Context Builder: LLM에게 실제 보여 줄 근거 선택
  ↓
Prompt: 원 질문 + 규칙 + 선택한 Context
  ↓
LLM: 답변 생성
  ↓
Validation / 출처 연결
  ↓
답변 + 출처 반환
```

**② 오늘 새로 배우는 RAG 평가 흐름**

```text
평가 질문과 정답 기준을 준비 (Dataset + Gold)
  ↓
평가할 RAG를 실행 (Target Runner)
  │  ※ Gold는 RAG에 전달하지 않음
  ↓
검색 후보·실제 Context·답변·출처·실행시간을 기록 (Run Record / Trace)
  ↓
실제 실행 결과와 미리 정한 정답을 비교 (Evaluator)
  ↓
검색 지표·답변 지표·운영 지표 산출
  ↓
질문별 실패 위치 분석 (Debugging)
  ↓
이전 버전과 개선 버전 비교 (Before / After)
  ↓
평가 보고서 작성 (Report)
  ↓
최소 품질 조건 확인 (Quality Gate)
```

**가장 중요한 차이:** 평가는 일반 사용자가 매 질문마다 반드시 거쳐야 하는 답변 단계가 아니라, **개발자가 품질을 검증하려고 별도로 실행하는 절차**다.

## A-3. 이번 수업의 핵심 구성요소 네 개

| 구성요소 | 아주 쉽게 말하면 | 결과 |
|---|---|---|
| **Dataset** | 시험지 + 채점에 쓸 정답 기준 | 질문, Gold 문서, 기준 답변 |
| **Target Runner** | 시험 문제를 기존 RAG에 실제로 물어보는 실행 담당 | 실제 검색·답변 결과 |
| **Evaluator** | 미리 정한 기준과 실제 결과를 비교하는 채점 담당 | 점수 및 통과·실패 판정 |
| **Report** | 어떤 질문에서 실패했고 무엇을 수정할지 정리한 성적표 | 질문별 문제와 개선 방향 |

# B. 평가 준비부터 보고서까지 — 절차 지향적으로 18단계

아래는 실제 사용자 질문의 RAG 실행 과정을 포함해서 **평가자가 전체 시스템을 어떻게 움직이는지** 순서대로 정리한 것이다.

## STEP 0. 검색에 사용할 문서와 기존 RAG가 미리 준비돼 있다

**누가:** 문서를 관리하는 프로그램과 개발자가 이전 수업에서 준비한 RAG 서비스  
**입력:** 출석·과제·시설 같은 원본 문서  
**결과:** Chunk 본문·벡터·Metadata가 PostgreSQL에 저장되고, RAG 서비스가 질문을 받을 수 있는 상태

- E5는 문서를 검색용 벡터로 변환해 저장하는 데 사용했다.
- PostgreSQL + pgvector는 저장된 벡터와 새 질문 벡터를 비교하는 데 사용한다.
- Day27의 Reranker는 검색된 후보를 추가 평가한다.
- **Day28은 이 기존 시스템을 평가한다.**

## STEP 1. 평가자가 시험할 질문들을 준비한다

**누가:** 개발자·평가 담당자·업무 내용을 아는 사람  
**입력:** 실제 서비스에서 나올 법한 질문과 해당 문서 집합  
**결과:** 평가용 질문 목록(Dataset)

예시:

- Q01: “회의실 신청과 취소는 어떻게 하나요?”
- Q02: “수업 시작 후 15분 지각 기준과 예외는 무엇인가요?”
- Q03: “회의실 예약을 어떻게 취소하나요?”
- Q04: “과제의 정확한 마감 날짜는 언제인가요?”

**이 질문들은 시험 문제다.** 아직 RAG에 입력한 것이 아니다.

## STEP 2. 질문마다 정답 문서(Gold Label)를 미리 결정한다

**누가:** 문서 내용을 확인한 사람(업무 전문가 또는 평가자)  
**입력:** 질문과 정확한 버전의 문서 원문  
**결과:** 관련 문서·Chunk의 ID 목록

| 질문 | 미리 지정한 Gold ID | 이유 |
|---|---|---|
| Q01 · 회의실 신청과 취소 | C3, C4 | 취소와 신청 근거 두 개가 필요 |
| Q02 · 15분 지각과 예외 | C1, C2 | 지각 기준과 예외 근거 필요 |
| Q03 · 회의실 취소 방법 | C3 | 취소 절차 근거 |
| Q04 · 정확한 과제 마감 날짜 | **없음(∅)** | 제공 문서에 정확한 날짜가 없음 |

- **Gold Label은 RAG가 검색하기 전에 정한다.**
- 실제 검색된 결과가 마음에 든다고 Gold를 뒤늦게 바꾸면 평가가 왜곡된다.
- 같은 문서라도 질문이 다르면 관련 여부가 달라질 수 있다.
- 한 질문에 정답 문서가 여러 개일 수 있다.

## STEP 3. 생성 답변을 비교할 기준 답변(Reference Answer)도 준비한다

**누가:** 평가자 또는 업무 전문가  
**입력:** 정답 원문·업무 규정  
**결과:** 질문별 기준 답변

예:

- Q01 Reference: “회의실 사용은 예약 승인을 받아야 하며, 취소하려면 운영실에 철회 요청을 전달한다.”
- Q04 Reference: “제공된 문서만으로 정확한 마감 날짜를 확인할 수 없다.”

**Gold Label과 Reference Answer는 다르다.**

- Gold는 **어떤 문서를 찾아야 했는가?**를 판단할 정답이다.
- Reference Answer는 **어떤 내용으로 답해야 했는가?**를 판단할 기준이다.

## STEP 4. 평가 조건과 실행 환경을 고정한다

**누가:** 평가 담당자  
**입력:** 평가 질문, 문서 집합, RAG 설정  
**결과:** 반복 가능한 실험 조건

가능한 한 같은 조건을 유지한다.

- 문서 집합과 버전(`corpus_version`)
- 평가 질문과 Gold Label
- Category·접근 권한 필터
- `candidate_k`, `context_k`
- E5·Reranker·LLM·Prompt 버전
- GPU·실행 환경·캐시 조건

왜 필요한가? **조건을 여러 개 바꾸면 결과가 달라져도 원인을 알기 어렵기 때문**이다.

## STEP 5. Target Runner가 평가할 기존 RAG에 질문을 입력한다

**누가:** Target Runner(평가용 실행 담당 프로그램)  
**입력:** Dataset에서 꺼낸 질문과 정상 검색 조건  
**결과:** 기존 RAG가 실제로 질문 처리 시작

**절대로 하지 말아야 하는 일:** Gold ID를 Retriever나 LLM에게 같이 넘기는 것.

```text
평가 Dataset
  ├─ question = “회의실 예약 취소 방법은?” ──→ RAG에 전달
  ├─ category = “시설” ───────────────────→ RAG에 전달
  └─ gold_chunk_ids = [C3] ──────────────→ 평가용으로만 별도 보관
```

Gold를 미리 보여 주면 시험 문제를 풀기 전에 정답지를 보여 주는 셈이다. 이를 **Gold Leakage**라고 한다.

## STEP 6. 기존 RAG가 질문을 검색용으로 정리한다

**누가:** Day27 Query Rewrite 단계  
**입력:** 원래 질문과 필요한 대화 History  
**결과:** 검색에 사용할 독립 질문(`search_query`)

예:

- 이전 대화: “회의실 예약 방법은?”
- 현재 질문: “그럼 취소는?”
- 검색용 질문: “회의실 예약을 취소하는 방법은?”

**원 질문은 보존한다.** 필요한 경우 표현을 확장해 여러 질의로 검색할 수 있지만, 없는 날짜·조건·권한을 새로 만들지 않는다.

## STEP 7. Retriever가 관련 문서 후보를 검색한다

**누가:** 기존 검색 기능(E5 모델, PostgreSQL, pgvector)  
**입력:** 검색용 질문, Category, 후보 개수  
**결과:** 후보 문서 목록(`candidate_ids`, `candidate_docs`)

실행 순서:

1. 검색 질문을 E5가 숫자 벡터로 변환한다.
2. PostgreSQL이 지정된 문서 범위와 현재 공개 버전 등의 조건을 적용한다.
3. pgvector를 이용해 질문과 저장된 문서 벡터의 거리를 비교한다.
4. 관련성이 높아 보이는 Chunk를 상위부터 가져온다.

예:

```text
후보 목록(candidate_ids)
C4 → C5 → C3
```

이것은 RAG가 **실제로 찾은 문서**다. **미리 정한 Gold와는 다른 데이터**다.

## STEP 8. Reranker가 후보 문서의 순서를 다시 평가한다

**누가:** Day27 Cross-Encoder Reranker  
**입력:** 검색용 질문 + 이미 검색된 후보 문서 목록  
**결과:** 새 순위(`ranked_ids`, `ranked_docs`)

예:

```text
Retriever 순위: C4 → C5 → C3
Reranker 순위:  C3 → C4 → C5
```

- Reranker는 질문과 각 후보 문서를 한 쌍으로 평가한다.
- **기존 후보의 순위만 조정할 수 있다.**
- 정답 C3가 애초에 검색 후보에 없었다면 Reranker가 C3를 새로 찾아낼 수 없다.

## STEP 9. Context Builder가 LLM에 실제 제공할 문서를 고른다

**누가:** Context Builder  
**입력:** 재정렬된 후보, 최대 개수, 길이 예산  
**결과:** `context`와 `included_ids`

예:

```text
재정렬 결과: C3 → C4 → C5
실제 Context: C3 → C4
included_ids = [C3, C4]
```

**오늘의 핵심 구분:**

- `candidate_ids`: 1차 검색 후보
- `ranked_ids`: 재정렬된 후보
- `included_ids`: **LLM이 실제로 받은 근거**

검색에 성공해도 Context에 정답이 빠질 수 있다. 이 경우는 첫 검색만의 문제가 아닐 수 있다.

## STEP 10. Prompt와 LLM이 근거 기반 답변을 생성한다

**누가:** LangChain Prompt 구성 단계와 Chat Model  
**입력:** 사용자 원 질문·답변 규칙·실제 Context  
**결과:** 자연어 답변과 생성 상태

- 검색용으로 바꿨던 질문이 아니라 **사용자가 원래 요청한 질문**을 기준으로 최종 답변을 만든다.
- Context에 없는 내용을 추측하면 Faithfulness 문제가 생길 수 있다.
- 원문에 답이 없는 질문에는 정보 부족이라고 답하는 것이 올바른 결과일 수 있다.

## STEP 11. Validator가 형식과 출처 ID를 확인한다

**누가:** RAG 서비스의 검증 코드  
**입력:** 모델 생성 결과와 `included_ids`  
**결과:** 정상 답변·정보 부족 상태 또는 명시적 오류

- 답변이 정상 완료됐는가?
- 정해진 Schema 형태인가?
- 답변에 포함된 출처 ID가 실제 Context의 ID인가?
- 잘못된 출처를 만들지는 않았는가?
- 오류를 정보 부족처럼 숨기지는 않았는가?

**Citation ID가 맞는 것과 답변 내용이 원문과 일치하는 것은 다르다.** 내용의 일치 여부는 별도의 평가 대상이다.

## STEP 12. 평가용 Trace가 중간 결과를 기록한다

**누가:** 평가용 Trace Adapter 및 실행 기록 장치  
**입력:** 기존 RAG 각 단계의 결과  
**결과:** 단계별 ID·순위·답변·상태·시간 기록

평가에 필요한 예시 항목:

| 항목 | 의미 |
|---|---|
| `question_id` | 어느 시험 문제인지 |
| `candidate_ids` | 첫 검색으로 찾은 문서 ID 순서 |
| `ranked_ids` | Reranking 후 순서 |
| `included_ids` | LLM에 실제 제공한 ID |
| `answer` | 생성한 답변 |
| `source_ids` | 답변이 인용한 출처 ID |
| `status` | 답변·정보 부족·오류 상태 |
| `latency_ms` | 처리에 걸린 시간 |

**Trace = 어떤 단계를 거쳐 무엇이 나왔는지 보여 주는 실행 기록.** 아직 좋은 결과인지 채점한 것은 아니다.

강의의 기존 서비스가 모든 중간값을 반환하지 않을 수 있어서 **평가용 Trace Adapter가 추가로 필요**하다. 필수 값이 없으면 결과가 0개인 척하지 말고 오류로 처리해야 한다.

## STEP 13. Target Runner가 실행 결과를 수집한다

**누가:** Target Runner  
**입력:** 기존 RAG 실행 완료 결과와 Trace  
**결과:** 질문 하나에 대한 Run Record

Run Record를 받았다면 **그때까지 별도로 보관한 Gold와 Reference를 평가 단계에서 결합**한다.

```text
평가용 질문 Q03
   ├─ 사전에 보관한 Gold: C3
   └─ 실제 실행 결과: C4 → C5 → C3
                    ↓
               Evaluator가 비교
```

**RAG의 답변을 만드는 주체와 평가 점수를 계산하는 주체를 섞어서 생각하지 않는다.**

## STEP 14. Evaluator가 검색 결과를 채점한다

**누가:** Retrieval Evaluator(평가 함수)  
**입력:** Gold 문서 ID와 실제 검색·재정렬·Context ID  
**결과:** Recall@k, Precision@k, Hit@k, RR, MRR, nDCG 등

Evaluator는 다음을 구분한다.

- **정답을 찾았는가?** → Hit@k
- **찾아야 할 정답 중 얼마나 찾았는가?** → Recall@k
- **상위 결과 중 얼마나 관련 있는가?** → Precision@k
- **첫 정답은 몇 위인가?** → RR / MRR
- **여러 관련 문서가 얼마나 좋은 순서로 정렬됐는가?** → nDCG

각 지표의 계산식은 **D장**에서 예제로 설명한다.

## STEP 15. Evaluator가 생성 답변을 별도로 평가한다

**누가:** Generation Evaluator, 필요 시 평가용 LLM 및 사람  
**입력:** 원 질문·실제 Context·생성 답변·Reference Answer  
**결과:** Faithfulness·Answer Relevance·Answer Correctness·Citation Validity 등

비교 대상이 서로 다르다.

1. **Faithfulness:** 답변의 개별 주장이 제공된 Context로 뒷받침되는가?
2. **Answer Relevance:** 답변이 원 질문에 적절히 답하는가?
3. **Answer Correctness:** 기준 답변과 실제 업무 사실에 맞는가?
4. **Citation Validity:** 인용한 ID가 실제 `included_ids` 안에 있는가?

**출처 ID만 맞으면 끝나는 것이 아니다.** 또한 평가용 LLM(LLM-as-a-Judge)은 보조 도구이며 사람이 직접 검수할 필요가 있다.

## STEP 16. 실패한 질문을 단계별로 진단한다

**누가:** 평가 담당자·개발자  
**입력:** 검색 지표, 생성 지표, 실행 Trace, 오류 상태  
**결과:** 문제의 원인 후보와 수정할 위치

예:

- 정답이 처음부터 후보에 없다 → Query Rewrite, Retriever, 문서/필터 확인
- 정답은 후보에 있지만 너무 뒤쪽이다 → Reranker 및 정렬 확인
- 정답은 Context 안에 있지만 LLM이 틀렸다 → Prompt, Generation, Grounding 확인
- 출처에 없는 ID를 반환했다 → Validator 확인
- 응답이 느리다 → GPU·DB·LLM 호출시간을 나누어 확인

**오답을 봤다고 무조건 LLM부터 바꾸지 않는다.**

## STEP 17. Baseline과 Improved를 같은 조건에서 비교한다

**누가:** 평가 담당자  
**입력:** 같은 질문셋으로 실행한 기존 버전·개선 버전 결과  
**결과:** 변경한 기능이 실제로 도움이 됐는지에 대한 판단

예를 들어 네 가지 경우를 비교할 수 있다.

| 버전 | Rewrite | Rerank | 보고 싶은 차이 |
|---|---|---|---|
| A · Baseline | OFF | OFF | 기존 수준 |
| B · Rewrite only | ON | OFF | 질문 변경의 영향 |
| C · Rerank only | OFF | ON | 같은 후보를 재정렬한 영향 |
| D · Both | ON | ON | 전체 개선 후 결과 |

- **한 번에 하나씩 바꾸는 비교**가 원인 분석에 유리하다.
- Rewrite가 질문을 바꿔 초기 후보까지 바뀌었다면 이를 Reranker만의 효과라고 할 수 없다.
- 이번 수업의 비교는 **오프라인 Paired Evaluation**이며 실제 사용자에게 무작위로 다른 버전을 보여 주는 온라인 A/B 테스트가 아니다.

## STEP 18. Report와 Quality Gate로 개선 여부를 결정한다

**누가:** 평가 담당자·팀·품질 검토 담당자  
**입력:** 질문별 점수, 실패 원인, 실행시간, 오류·권한 결과  
**결과:** 평가 리포트와 다음 단계 진행 가능 여부

평가 보고서에는 다음을 남긴다.

- 평가한 질문과 Gold·문서 버전
- 검색·답변 평가 점수
- 질문별 실패 이유
- 개선 전후의 차이
- 어느 모듈을 고칠지
- 모델·GPU·실행 시각·Latency·오류 코드
- 정해 둔 최소 품질 조건 통과 여부

**Quality Gate는 “다음 단계로 넘어가기 전에 통과해야 하는 검사 기준”**이다. 다만 수업의 일부 점수 기준을 통과했다고 실제 Agent 배포가 자동 승인되는 것은 아니다.

# C. 오늘 꼭 알아야 할 기본 개념

## C-1. Evaluation은 왜 필요한가?

사용자에게 답변이 돌아왔다는 사실만으로 RAG가 잘 작동했다고 볼 수 없기 때문이다.

문제가 발생하는 예:

- 관련 문서를 검색하지 못했다.
- 검색은 했지만 정답 문서가 너무 뒤에 있었다.
- 정답 문서는 LLM에게 줬지만 LLM이 틀린 답변을 만들었다.
- 답변이 실제 없는 출처를 인용했다.
- 답변은 맞지만 20초나 걸렸다.

**따라서 검색, 순위, 생성, 출처, 성능을 분리해서 평가해야 한다.**

## C-2. Debugging이란?

문제가 난 뒤 **어느 단계가 원인인지 찾고 고칠 부분을 판단하는 과정**이다.

단순히 결과가 틀렸다고 고치는 것이 아니라, 실행 기록과 평가 지표를 보고 **실패 지점**을 좁힌다.

## C-3. Dataset은 시험지다

여러 질문과 정답 기준을 모아 놓은 평가용 데이터다. 같은 시험지를 여러 번 사용해야 버전 간 비교가 가능하다.

## C-4. Gold Label은 검색 정답지다

사람이 원문을 검토한 뒤 **그 질문에 관련된 문서·Chunk ID**를 미리 지정한 것이다.

Gold는 검색 결과가 아니라 **비교 기준**이다.

## C-5. Reference Answer는 답변 정답지다

LLM의 최종 답변이 업무상 맞는지 비교하기 위한 기준 문장이다.

- Gold = **어떤 문서를 찾아야 했는지**
- Reference = **무엇이라고 답해야 했는지**

## C-6. No-answer도 좋은 테스트 문제다

정답 문서가 아예 없는 질문을 평가에 포함한다.

예: 문서에 과제의 정확한 마감 날짜가 없다면 “확인할 수 없다”가 올바른 답이다.

- Gold가 비어 있을 때 Recall@k는 **0이 아니라 N/A(계산 대상 아님)**이다.
- 정보 부족 응답을 했는지 별도로 평가한다.
- DB 접속 실패나 API 오류는 정보 부족으로 위장하지 않는다.

## C-7. Binary Relevance와 Graded Relevance

- **Binary:** 관련 있으면 1, 아니면 0.
- **Graded:** 관련성 정도를 0(무관)·1(부분 관련)·2(매우 관련) 등으로 구분.

Recall과 MRR은 관련 여부를, nDCG는 관련 정도와 문서의 위치를 함께 고려하는 데 사용한다.

## C-8. Gold Leakage가 왜 위험한가?

정답을 평가 대상에게 알려 주면 실제 검색 능력을 확인할 수 없게 된다.

예를 들어 Retriever가 원래는 C3를 찾아야 하는데 시험 실행할 때 C3가 Gold라고 알려 주면 결과가 좋아 보이더라도 공정한 평가가 아니다.

## C-9. Candidate Recall과 Context Recall

- **Candidate Recall:** 처음 검색한 후보들 안에 정답이 얼마나 있는가?
- **Context Recall:** LLM에게 실제 넣어 준 문서들 안에 정답이 얼마나 있는가?

후보에는 정답이 있어도 Context 길이 제한이나 재정렬 때문에 빠질 수 있다.

## C-10. Trace와 Evaluation은 다르다

- **Trace:** 시스템이 **어떻게 실행됐는지** 남긴 기록.
- **Evaluation:** 기록된 결과가 **좋은지** 기준과 비교하는 채점.

Trace를 저장했다고 품질이 검증된 것은 아니다.

## C-11. Retrieval과 Generation은 분리해 평가한다

- **Retrieval 평가:** 문서를 올바르게 찾았는가, 정답 문서를 앞에 배치했는가?
- **Generation 평가:** LLM 답변이 질문·원문 근거·기준 정답과 맞는가?

검색이 나빠서 답이 틀릴 수도 있고, 검색이 좋아도 답변을 잘못 만들 수도 있다.

## C-12. LLM-as-a-Judge는 무엇인가?

다른 LLM 또는 평가용 LLM에게 “이 답변은 근거와 일치하는가?”처럼 평가를 맡기는 방법이다.

단, 평가용 LLM도 틀릴 수 있다. **사실의 최종 판사로 과신하지 않고, 사람 검토와 비교한다.** 비용과 민감 정보 취급에도 주의한다.

## C-13. A/B 비교는 무엇인가?

기존 방식(Baseline)과 수정한 방식(Improved)을 **같은 평가 조건에서** 시험해 차이를 확인하는 방법이다.

질문·Gold·Corpus·검색 권한·k·모델 버전 등을 고정하고, 가능한 한 한 가지 기능만 바꿔야 원인을 설명하기 쉽다.

## C-14. Quality Gate는 무엇인가?

정해 둔 점수와 운영·권한 조건을 통과하지 못하면 다음 단계 연결을 보류하는 검사 기준이다.

**높은 Recall만으로 충분하지 않다.** Faithfulness, 답변 정확성, 출처, No-answer, Latency, 오류 처리, 권한 위반도 살펴봐야 한다.

# D. 검색 평가 지표 — 수식과 실제 계산을 초보자용으로

지표를 외우기 전에 아래 두 목록을 먼저 구분한다.

- **Gold:** 사람이 미리 지정한 관련 문서 집합.
- **Top-k:** RAG가 실제로 반환한 상위 k개 결과.

하나의 공통 예시를 사용해 보자.

```text
Gold 정답 문서: C1, C2, C3
실제 Top-3:    C4, C2, C1
```

원래 찾았어야 하는 문서는 3개이고, 실제 Top-3에서 C2와 C1 두 개를 찾았다.

## D-1. Hit@k — 정답이 최소 한 개라도 있었나?

**질문:** 상위 k개 안에 Gold 문서가 하나라도 있는가?

- 있으면 **1**.
- 없으면 **0**.
- 위 예에서는 C2·C1이 있으므로 **Hit@3 = 1**.

**주의:** Hit@3이 1이라고 Gold를 모두 찾은 것은 아니다.

## D-2. Recall@k — 찾아야 할 정답 중 몇 개를 찾았나?

**계산:** `Top-k에 포함된 Gold 개수 ÷ 전체 Gold 개수`

공통 예시:

- Gold 전체 = 3개(C1·C2·C3)
- Top-3에 실제 포함된 정답 = 2개(C1·C2)
- **Recall@3 = 2 ÷ 3 ≈ 0.667 (66.7%)**

**기억:** Recall의 분모는 *전체 Gold 문서 수*다.

### 예외: Gold가 비어 있으면?

골드 문서가 0개라면 분모가 0이므로 **Recall@k = N/A**다. 이 질문은 No-answer 동작을 따로 평가한다.

## D-3. Precision@k — 가져온 상위 결과 중 몇 개가 관련 있나?

**계산(이번 강의의 정의):** `Top-k에 포함된 Gold 개수 ÷ k`

공통 예시:

- 상위 결과 3개 중 관련 문서 2개.
- **Precision@3 = 2 ÷ 3 ≈ 0.667 (66.7%)**.

**기억:** 이 수업의 Precision@k 분모는 **항상 k**다. 실제 반환된 문서 수가 k보다 적더라도 k를 사용한다.

## D-4. Hit·Recall·Precision 비교표

| 지표 | 무엇을 알고 싶은가? | 이번 공통 예시 |
|---|---|---|
| **Hit@3** | 하나라도 찾았나? | **1** |
| **Recall@3** | Gold 전체 중 얼마나 찾았나? | **2/3 = 0.667** |
| **Precision@3** | 상위 3개 중 얼마나 관련 있나? | **2/3 = 0.667** |

이 예시에서는 Recall과 Precision이 우연히 같다. **두 지표가 같은 뜻이라는 의미는 아니다.**

### 서로 다르게 나오는 예

```text
Gold: C1, C2, C3, C4 (4개)
Top-5: C1, C2, C7, C8, C9 (관련 2개)
```

- Recall@5 = **2/4 = 0.5**
- Precision@5 = **2/5 = 0.4**
- Hit@5 = **1**

## D-5. RR(Reciprocal Rank) — 첫 정답이 몇 위인가?

RR은 한 질문에서 **맨 처음 등장하는 정답 문서의 순위**를 평가한다.

**계산:** `RR = 1 ÷ 첫 정답 순위`

| 첫 정답 위치 | RR |
|---|---:|
| 1위 | 1.000 |
| 2위 | 0.500 |
| 3위 | 0.333 |
| 4위 | 0.250 |
| Top-k에 정답 없음 | 0.000 |

왜 쓰나? 답변에 사용할 근거가 상위 2~3개만 선택될 수 있으므로 **관련 문서가 앞에 나오는 것**이 중요하기 때문이다.

## D-6. MRR(Mean Reciprocal Rank) — 여러 질문의 RR 평균

RR은 질문 **한 개**의 점수고, **MRR은 여러 질문의 RR을 평균**낸 값이다.

예시:

| 질문 | 첫 정답 위치 | RR |
|---|---|---:|
| Q1 | 1위 | 1.000 |
| Q2 | 3위 | 0.333 |
| Q3 | 2위 | 0.500 |
| Q4 | Top-k에 없음 | 0.000 |

- MRR = `(1.0 + 0.333 + 0.5 + 0.0) ÷ 4 ≈ 0.458`
- **MRR은 첫 관련 문서만 본다.** 두 번째·세 번째 관련 문서가 얼마나 앞에 왔는지까지 충분히 설명하지 못한다.
- No-answer 질문을 MRR 평균에 넣을지 여부는 **평가셋 정책으로 미리 정해야** 한다.

## D-7. DCG — 관련성이 높은 문서를 앞에 둔 정도

MRR은 첫 정답만 보기 때문에 관련 문서가 여러 개인 상황을 충분히 평가하기 어렵다.

DCG는 **각 문서의 관련성 등급**과 **검색 순위**를 함께 반영한다.

- 높은 등급(예: 2)이 낮은 등급(예: 1)보다 점수를 더 많이 얻는다.
- 같은 등급의 문서라도 뒤쪽 순위에 있으면 기여점수가 줄어든다.

원본 강의의 공식:

`DCG@k = Σ [(2^grade − 1) / log₂(rank + 1)]`

용어:

- `grade`: 사람이 부여한 관련성 등급(0·1·2)
- `rank`: 검색 순위(1위·2위·3위…)
- `2^grade − 1`: 높은 관련성 등급에 더 많은 점수를 주는 방식(Gain)
- `log₂(rank + 1)`: 뒤쪽 문서의 점수를 낮추는 순위 할인

## D-8. IDCG와 nDCG — 이상적인 순위와 얼마나 비슷한가?

- **IDCG:** 관련성 등급을 가장 좋은 순서대로 배치했을 때의 DCG.
- **nDCG:** 실제 DCG를 이상적인 IDCG와 비교한 비율.

`nDCG@k = DCG@k ÷ IDCG@k`

원본 강의의 교육용 예:

```text
Gold 관련성 등급: C3 = 2, C1 = 1, C2 = 0
실제 검색 순위:   1위 C1, 2위 C2, 3위 C3
이상적인 순위:    1위 C3, 2위 C1, 3위 C2
```

**실제 검색 순위의 DCG:**

| 순위 | 문서 | 등급 | 기여점수 |
|---|---|---:|---:|
| 1위 | C1 | 1 | 1.000 |
| 2위 | C2 | 0 | 0.000 |
| 3위 | C3 | 2 | 1.500 |
| 합계 | | | **DCG = 2.500** |

**이상적인 순위의 IDCG:**

- C3(등급 2)를 1위에 두면 기여 3.000
- C1(등급 1)을 2위에 두면 기여 약 0.631
- 합계 **IDCG ≈ 3.631**

따라서 **nDCG@3 = 2.500 / 3.631 ≈ 0.689**.

**왜 필요할까?** 정답 문서가 여러 개이고 중요한 정도도 다를 때, *어떤 문서가 어느 순서에 있는지*까지 평가하려고.

**주의:** 관련 등급이 전부 0이면 IDCG가 0이므로 nDCG를 N/A로 관리한다. 원본의 교육용 코드는 등급 미지정 문서를 0으로 가정하지만, 실제 평가에서는 **미판정 문서**와 **무관 판정 문서**를 구분해야 한다.

## D-9. Reranking 전후에 Recall은 같고 MRR은 달라질 수 있다

예:

```text
Gold = C3
Baseline 순위: C4 → C5 → C3
Rerank 순위:   C3 → C4 → C5
```

- 두 경우 모두 Top-3에 C3가 있으므로 **Recall@3 = 1.0**.
- Baseline RR = **1/3**.
- Rerank RR = **1/1 = 1.0**.

즉, **정답을 찾았는지**와 **정답을 앞에 놓았는지**는 다른 평가다.

# E. 생성 답변 평가는 문서 검색 평가와 다르다

## E-1. 왜 검색 성능만 평가하면 안 될까?

정답 문서 C1을 정확하게 검색하고 Context에 넣어도 LLM이 문서의 숫자나 예외를 잘못 읽을 수 있다.

따라서 최종 답변은 **별도 평가**가 필요하다.

## E-2. 생성 평가 지표 네 가지

| 지표 | 비교하는 대상 | 실제로 묻는 질문 |
|---|---|---|
| **Faithfulness(충실성)** | 생성 답변의 주장 ↔ 실제 Context | 문서가 이 주장을 뒷받침하는가? |
| **Answer Relevance(질문 관련성)** | 원래 질문 ↔ 생성 답변 | 사용자가 물은 것에 답했는가? |
| **Answer Correctness(정답성)** | 생성 답변 ↔ Reference Answer·사실 | 기준 정답과 일치하는가? |
| **Citation Validity(출처 유효성)** | 인용한 출처 ID ↔ 실제 `included_ids` | 모델이 읽은 문서만 인용했는가? |

**이 네 가지는 서로 다른 검사다.**

## E-3. Claim(주장) 단위로 나누는 이유

답변 한 문장에 여러 주장이 섞여 있을 수 있다.

예:

> “15분까지는 지각이고, 15분 초과는 결석이며, 벌금은 5만원입니다.”

개별 Claim으로 나누면:

1. 15분까지 지각 → **원문에서 확인 가능**
2. 15분 초과 결석 → **원문에서 확인 가능**
3. 벌금 5만원 → **원문에 없음**

기본 교육용 방식으로는:

- 총 Claim 3개
- 문서가 뒷받침하는 Claim 2개
- **Faithfulness = 2/3 ≈ 0.667**

Claim이 0개라면 이를 100% 충실하다고 보지 않고 **N/A**로 다루는 예시가 제시된다.

주의: 실제 자동 평가 도구는 Claim 추출 방식과 지지 판정 기준에 따라 점수가 달라질 수 있다.

## E-4. Faithfulness와 Relevance는 동시에 높지 않을 수도 있다

사용자 질문: “과제 제출 기한이 언제인가요?”

실제 Context: “회의실 예약은 운영실 승인이 필요합니다.”

모델 답변: “회의실 예약은 운영실 승인이 필요합니다.”

- **Faithfulness:** 전달된 문서와 답변은 일치하므로 높게 나올 수 있다.
- **Answer Relevance:** 과제 제출 기한 질문에 답하지 않으므로 낮다.

**근거와 일치하는 답변이라고 해서 반드시 질문에 적절한 답변은 아니다.**

## E-5. Correctness는 무엇을 더 확인하나?

사용자 질문: “정확한 과제 마감 날짜는?”

제공 문서: “마감 날짜는 담당자가 공지한 날짜를 따릅니다.”

- “내일 오후 6시입니다.” → 질문에는 직접 답하지만 **근거에 없는 날짜를 지어낸 것**.
- “제공된 문서에는 정확한 날짜가 없습니다.” → **No-answer 정책과 부합**.

정확한 사실과 조건은 Reference Answer 및 필요 시 업무 담당자의 검토로 확인한다.

## E-6. Citation과 Grounding 차이 다시 정리

- **Citation Validity:** `source_ids=[C3]`에서 C3가 실제 Context에 있었는가?
- **Grounding/Faithfulness:** 답변에 적은 ‘취소 절차’가 실제 C3 본문과 일치하는가?

**ID가 존재한다는 이유만으로 답변 내용을 정답이라고 판단하면 안 된다.**

## E-7. 평가용 LLM은 보조적인 판정 수단이다

평가용 LLM이 문서와 Claim을 읽고 `supported`/`reason` 같은 판단 결과를 반환하도록 할 수 있다.

그러나:

- LLM이 틀리게 판정할 수 있다.
- 생성 모델과 평가 모델이 같으면 비슷한 편향을 공유할 수 있다.
- 외부 서비스로 자료를 보낼 때 비용·시간·개인정보·접근 권한을 확인해야 한다.
- **사람 검수(Human Review)**가 필요하다.

# F. 결과가 나쁠 때 어디를 고쳐야 하나? — Debugging 지도

## F-1. 지표와 실패 위치 연결

| 관찰된 문제 | 가장 먼저 확인할 위치 | 이유 |
|---|---|---|
| **Recall@k 낮음** | Query Rewrite, Retriever, Category/Version Filter, Indexing | 정답이 첫 검색 후보에 없을 수 있음 |
| **Recall은 높은데 MRR 낮음** | Reranker, 순위, Top-N | 정답을 찾았지만 뒤쪽에 배치했을 수 있음 |
| **Candidate Recall 높고 Context Recall 낮음** | Reranker, Context Builder, 길이 예산 | 찾았던 정답이 실제 근거에서 빠짐 |
| **Faithfulness 낮음** | Prompt, Generator, 근거 해석 | 문서에 없는 주장을 생성했음 |
| **Answer Relevance 낮음** | 질문 이해, Rewrite, Context 선택, Generation | 질문과 다른 답변을 했음 |
| **Correctness 낮음** | 원문 버전, Reference, Generator | 조건·숫자·예외가 실제 기준과 다름 |
| **Citation Validity 실패** | Validator, `included_ids` 관리 | 전달하지 않은 문서를 출처로 표시 |
| **No-answer인데 사실을 만들어 답함** | Prompt, 정보 부족 처리, Generation | 답할 수 없을 때 보류하지 못함 |
| **Latency 증가** | Rewrite LLM, 다중 검색, DB, Cross-Encoder GPU, 생성 LLM | 호출 수·추론 시간이 늘었을 수 있음 |
| **401·Timeout·OOM·DB 오류** | 인증·서버·GPU·연결·예외 처리 | 검색 정확도와 별개인 시스템 실패 |

## F-2. 대표적인 네 가지 사례

### 사례 1. 정답이 검색 후보에 아예 없다

```text
Gold: C3
Retriever 후보: C1, C2, C4
```

**문제 위치:** Retriever 이전 질문 표현, 검색 필터, Corpus/Indexing, 후보 수.

**잘못된 해결:** Reranker만 추가하면 C3를 찾을 수 있다고 생각하기.

### 사례 2. 정답은 있는데 순위가 너무 낮다

```text
Gold: C3
Retriever 후보: C1, C2, C3
실제 Context: C1, C2
```

정답 C3가 후보에는 있었지만 LLM은 받지 못했다.

**문제 위치:** Reranker 또는 Context Builder의 선택 기준.

### 사례 3. 올바른 문서를 줬는데 LLM이 답을 틀렸다

```text
Context: “15분까지 지각, 15분 초과 결석”
LLM: “20분까지 지각입니다.”
```

**문제 위치:** Prompt·LLM Generation·Grounding 확인.

### 사례 4. 답변이 맞아도 서비스가 너무 느리다

검색과 답변은 정상이어도 Rewrite LLM 호출, 여러 차례의 DB 검색, Cross-Encoder 추론 등이 추가되어 지연될 수 있다.

**문제 위치:** 각 Stage별 Latency와 자원 사용.

## F-3. Latency는 무엇을 재는가?

**Latency = 요청 처리가 시작되어 끝날 때까지 걸린 시간**이다.

세부적으로 나눠 보면:

- Rewrite에 걸린 시간
- E5 질문 벡터 생성 시간
- PostgreSQL 검색 시간
- Cross-Encoder Reranking 시간
- Prompt/LLM API 호출 시간
- 검증과 결과 구성 시간

원본 자료에서는 **CUDA GPU 작업은 비동기일 수 있기 때문에 정확한 GPU 실행시간 측정에는 동기화가 필요하다**고 설명한다. DB·원격 API 호출과 동일한 방식으로 GPU 시간까지 단정하지 않는다.

## F-4. 높은 점수와 좋은 서비스는 완전히 같지 않다

예를 들어 Recall이 좋아졌어도:

- 지연시간이 크게 늘 수 있다.
- 외부 모델 API 비용이 증가할 수 있다.
- 이전에 잘 맞던 질문이 틀릴 수 있다.
- 허용되지 않은 문서가 검색될 수 있다.

그래서 **점수 + 질문별 실패 + 지연·비용 + 권한·오류**를 함께 본다.

# G. Before/After 비교와 Quality Gate

## G-1. 비교할 때 무엇을 고정해야 하나?

- 같은 질문과 Gold
- 같은 Corpus Version
- 같은 문서 접근·권한 조건
- 같은 Category
- 같은 Candidate-k와 Context-k
- 동일하게 설명 가능한 모델·Prompt·실행 환경

원본 강의는 **Rewrite만**, **Rerank만**, **둘 다**를 구분해 비교하도록 안내한다.

## G-2. 교육용 비교 사례 읽기

질문: “회의실 취소 방법은?” / Gold: C3 / k=3.

| 실험 | Top-3 후보 | Recall@3 | RR@3 | 시연용 Latency |
|---|---|---:|---:|---:|
| A · 기존 | C4, C5, C3 | 1.000 | 0.333 | 820ms |
| B · Rewrite만 | C3, C4, C5 | 1.000 | 1.000 | 1,190ms |
| C · Rerank만 | C4, C3, C5 | 1.000 | 0.500 | 980ms |
| D · 둘 다 | C3, C4, C5 | 1.000 | 1.000 | 1,390ms |

**이 숫자는 실제 GPU·DB·LLM 측정값이 아닌 강의의 고정 시뮬레이션 값이다.**

읽는 법:

1. 네 경우 모두 C3가 Top-3에 있으므로 Recall은 같다.
2. C3의 위치가 바뀌었으므로 RR은 다르다.
3. 개선 기능이 추가되면 시연상 Latency가 커진다.
4. 한 번의 사례로 전체 서비스가 좋아졌다고 단정할 수 없다.

## G-3. 평균만 보면 왜 위험할까?

예를 들어 전체 평균 Recall은 높아졌지만, 특정 질문에서 Rewrite가 원래 의미를 바꿔 정답이 사라질 수 있다.

따라서 **질문별 Drill-down(자세히 들여다보기)**이 필요하다.

평가 보고서에는 어떤 질문에서 어떤 문제가 일어났는지, 해당 실행의 정답과 검색 후보·Context·모델 버전·시간을 함께 남긴다.

## G-4. Quality Gate의 예시

원본의 1차 Release Gate 예시 조건:

| 조건 | 교육용 기준 |
|---|---|
| Mean Recall | 0.70 이상 |
| Mean MRR | 0.60 이상 |
| 잘못된 출처 ID | 0건 |
| 권한 위반 | 0건 |

단, 별도로 제시된 **교육용 평가 보고서**에서는 목표치를 `Recall@3 ≥ 0.80`, `MRR@3 ≥ 0.60`으로 둔다.

**두 값은 서로 다른 교육용 예시 기준이므로 섞으면 안 된다.** 실제 서비스의 품질 기준은 업무 성격과 운영 정책에 따라 별도로 정의한다.

또한 위 네 조건을 모두 통과해도 다음 항목은 추가로 확인해야 한다.

- 답변 Faithfulness와 Correctness
- No-answer 처리
- 생성 오류와 DB/모델 API 오류 구분
- 실제 Latency·비용
- 보안·권한·원문 출처
- 필요할 때 사람 검수

**Quality Gate 통과 ≠ 실제 Agent 배포 승인.**

# H. 강의의 평가 예시 4건을 실제로 읽어 보기

원본 자료의 *교육용 합성 Dataset*에는 다음 사례가 있다.

| 평가 질문 | Gold | Top-3 검색 순위 | Recall@3 | RR@3 |
|---|---|---|---:|---:|
| Q01 · 회의실 신청·취소 | C3, C4 | C5 → C3 → C6 | 0.500 | 0.500 |
| Q02 · 15분 지각·예외 | C1, C2 | C7 → C2 → C9 | 0.500 | 0.500 |
| Q03 · 회의실 취소 방법 | C3 | C4 → C5 → C3 | 1.000 | 0.333 |
| Q04 · 정확한 과제 마감 날짜 | ∅ | C7 → C9 → C10 | N/A | 별도 No-answer 평가 |

## H-1. Q01이 왜 Recall 0.5인가?

Gold는 C3·C4 **두 개**다.

하지만 Top-3에는 C3만 있고 C4는 없다.

따라서 **1개 / 2개 = 0.5**다.

첫 관련 문서 C3가 **2위**이므로 RR은 **1/2 = 0.5**다.

## H-2. Q03은 왜 Recall이 높아도 RR이 낮나?

Gold는 C3 한 개이고 Top-3에 C3가 있으므로 Recall@3은 **1.0**이다.

그런데 C3가 **3위**에 있으므로 RR은 약 **0.333**이다.

**찾기에는 성공했지만 높은 순위로 올려놓는 데는 부족한 상황**이다.

## H-3. Q04는 왜 Recall 0이 아니야?

이 질문에서 답할 수 있는 정확한 날짜가 제공 문서에 없다.

따라서 Gold가 비었고, Recall의 분모가 0이므로 **N/A**다.

대신 시스템이 날짜를 지어내지 않고 **`insufficient_context`**를 반환하는지 확인해야 한다.

## H-4. 위 예시의 평균값

Q01~Q03만 검색 평가 평균에 포함한다.

- **Mean Recall@3 = (0.5 + 0.5 + 1.0) / 3 ≈ 0.667**
- **Mean Precision@3 = (1/3 + 1/3 + 1/3) / 3 ≈ 0.333**
- **MRR@3 = (0.5 + 0.5 + 0.333) / 3 ≈ 0.444**

원본의 교육용 보고서는 이 점수에 대해 **“개선 후 재평가 필요”**라고 결론 내린다.

**주의:** 이는 고정 예시 순위에 공식을 적용한 결과다. 실제 사용자의 PostgreSQL·GPU·LLM을 실행한 측정 결과가 아니다.

# I. 용어 사전 — Day28 핵심 용어를 주제별로

## I-1. 평가 일반·데이터 용어

| 용어 | 초보자용 의미 | 예시·기억법 |
|---|---|---|
| **RAG Evaluation** | RAG가 정답 문서를 찾고 맞게 답하는지 검사하는 일 | 검색·답변·출처·Latency 평가 |
| **Debugging** | 실패 위치를 찾고 원인을 수정하는 일 | 검색 실패와 생성 실패 구분 |
| **Dataset** | 평가에 사용할 질문과 정답 기준 모음 | 시험지 + 정답 기준 |
| **Target** | 평가 대상 프로그램·모델·서비스 | Day27 Enhanced RAG |
| **Target Runner** | Dataset 질문을 Target에 입력하고 결과를 수집하는 실행 담당 | 시험 응시를 진행하는 감독관 |
| **Evaluator** | Target 결과를 정답 기준과 비교해 점수를 계산하는 기능 | 채점자 |
| **Report** | 결과·실패·개선점을 모은 평가 보고서 | 성적표와 수정 계획 |
| **Gold Label** | 사람이 미리 정한 관련 문서·Chunk 정답 ID | `Gold={C3,C4}` |
| **Reference Answer** | LLM 최종 답변과 비교할 기준 문장 | 승인·취소 절차의 정답 설명 |
| **Judgment** | 질문과 문서가 관련 있는지를 판단한 레이블 | C3 관련, C5 무관 |
| **Binary Relevance** | 관련 1, 무관 0으로 나타낸 판정 | Recall·MRR 계산에 활용 |
| **Graded Relevance** | 관련성 수준을 등급으로 구분한 판정 | 0·1·2등급 |
| **No-answer** | 현재 자료만으로 답할 수 없는 평가 질문 | 정확한 날짜가 없음 |
| **Gold Leakage** | 평가 정답이 검색·생성 입력 또는 튜닝에 새어 들어가는 문제 | 정답을 미리 보여 줌 |
| **Corpus** | 검색 대상 문서 모음 | 시설·출석·과제 문서 전체 |
| **Corpus Version** | 평가에 사용한 문서 집합의 버전 | `policy_2026_v2` |
| **Dataset Split** | 학습·개선용과 최종 평가용 질문을 분리하는 것 | 평가 문제 반복 노출 방지 |
| **Run Record** | 질문 한 건의 입력·실제 결과·상태·시간 기록 | Q01의 후보·답변·지연 |
| **Trace** | 실행 단계별 값·시간·오류를 순서대로 추적한 기록 | Rewrite → Retrieve → Rerank |
| **Trace Adapter** | 기존 RAG에서 평가에 필요한 중간 결과를 꺼내는 연결 장치 | `candidate_ids`, `included_ids` 확보 |

## I-2. 검색·순위·지표 용어

| 용어 | 초보자용 의미 | 예시·기억법 |
|---|---|---|
| **Retriever** | 질문과 관련된 Chunk 후보를 검색하는 기능 | E5·pgvector 기반 검색 |
| **Reranker** | 검색된 후보를 다시 평가해 순서를 정하는 기능 | Cross-Encoder |
| **Top-k** | 검색 순위의 상위 k개 | Top-3 |
| **Candidate-k** | 첫 Retriever에서 가져오는 최대 후보 수 | 후보 10개 |
| **Context-k** | LLM에게 실제 보여 줄 근거의 최대 개수 | 근거 3개 |
| **Candidate Set** | 최초 검색으로 확보한 후보 집합 | C1·C2·C3 |
| **Candidate Recall** | 첫 후보 목록 기준으로 계산한 정답 포함률 | Reranker가 받을 정답의 양 |
| **Context Recall** | LLM에 실제 포함된 문서 기준 정답 포함률 | 빠진 정답 확인 |
| **Hit@k** | 상위 k개 안에 정답이 하나라도 있는지 | 있으면 1, 없으면 0 |
| **Recall@k** | 전체 Gold 중 Top-k에서 찾아낸 비율 | 2/4 = 0.5 |
| **Precision@k** | 상위 k개 중 정답 문서의 비율 | 이 수업은 분모 k |
| **RR** | 첫 관련 문서가 나온 순위의 역수 | 3위 → 1/3 |
| **MRR** | 여러 질문의 RR을 평균낸 값 | 여러 질문의 첫 정답 위치 평균 |
| **Gain** | 문서 관련성 등급을 점수로 바꾼 이득 | `2^grade - 1` |
| **DCG** | 관련성 등급과 순위 할인을 합친 점수 | 좋은 근거가 앞에 있는 정도 |
| **IDCG** | 같은 관련성 등급의 이상적인 최고 DCG | 최적 정렬 기준 |
| **nDCG** | 실제 DCG를 IDCG로 나눈 상대 점수 | 0.689 같은 정규화 점수 |
| **Ranking** | 검색 결과를 관련성 순서로 배치하는 것 | C3가 3위인지 1위인지 |
| **Recall Ceiling** | 처음 후보에 정답이 없으면 재정렬로 복구할 수 없는 한계 | 후보 밖 C3는 Rerank 불가 |
| **Gold ∅** | 정답 문서 집합이 비어 있는 상태 | Recall N/A |

## I-3. 생성·근거·출처 평가 용어

| 용어 | 초보자용 의미 | 예시·기억법 |
|---|---|---|
| **Generation Evaluation** | LLM이 만든 답변의 품질을 검사 | 충실성·관련성·정답성 |
| **Faithfulness** | 답변 주장이 실제 Context로 뒷받침되는 정도 | 문서에 없는 벌금 주장은 실패 |
| **Answer Relevance** | 답변이 사용자의 질문에 적절하게 답했는지 | 과제 날짜 질문에 과제 이야기 |
| **Answer Correctness** | 답변이 기준 정답·사실과 맞는지 | 숫자·기한·예외 정확성 |
| **Citation Validity** | 답변의 출처 ID가 실제 제공된 ID인지 | `source_ids` ↔ `included_ids` |
| **Claim** | 참·거짓이나 근거 여부를 확인할 수 있는 개별 주장 | “15분 초과는 결석” |
| **Grounding** | 답변 내용이 실제 근거 문서에 기반하는지 확인하는 관점 | 출석 규정 대조 |
| **LLM-as-a-Judge** | LLM을 평가 보조자로 사용 | 문장·근거 쌍을 평가 모델에 제시 |
| **Human Review** | 사람이 문서와 답변을 직접 비교·검수 | 예외 규정 확인 |
| **Structured Output** | 정해 둔 자료형·구조로 모델 응답을 받는 방식 | 지원 여부·판정 이유 |
| **Pydantic** | Python 데이터의 필드·자료형을 검사하는 라이브러리 | 평가 결과 Schema |
| **Source ID** | 모델 답변의 출처를 가리키는 식별값 | `source_ids` |
| **included_ids** | 실제 LLM Context에 포함된 문서 ID | 인용 가능 범위의 기준 |
| **insufficient_context** | 확인할 근거가 부족해 정상적으로 답변을 보류한 상태 | 정확한 과제 마감일 모름 |

# J. 자주 혼동하는 개념 15쌍

| 헷갈리는 두 용어 | 정확한 차이 |
|---|---|
| **Dataset vs Gold** | Dataset은 질문과 정답 기준의 전체 모음. Gold는 그 안에서 관련 문서 ID를 지정한 정답 기준. |
| **Gold vs Retrieved IDs** | Gold는 사람이 미리 정한 정답. Retrieved IDs는 실제 검색에서 나온 결과. |
| **Gold vs Reference Answer** | Gold는 찾아야 할 문서. Reference는 답해야 할 내용. |
| **Gold vs Citation ID** | Gold는 평가 정답 문서의 식별값. Citation ID는 서비스가 답변 출처로 관리하는 식별값. 식별자 대응 관계를 확인해야 한다. |
| **Candidate IDs vs Included IDs** | 전자는 1차 검색 후보, 후자는 LLM에게 실제 전달한 근거. |
| **Retriever vs Reranker** | Retriever는 후보를 찾고, Reranker는 찾은 후보의 순위를 바꾼다. |
| **Hit@k vs Recall@k** | Hit은 하나라도 있었는지, Recall은 전체 정답 중 몇 개를 찾았는지. |
| **Recall@k vs Precision@k** | Recall 분모는 Gold 수, Precision 분모는 k(이번 수업). |
| **RR vs MRR** | RR은 질문 하나의 첫 정답 순위 점수, MRR은 여러 질문의 RR 평균. |
| **MRR vs nDCG** | MRR은 첫 정답만, nDCG는 여러 문서의 관련성 등급과 위치. |
| **Faithfulness vs Relevance** | 원문에 맞는 답이더라도 사용자 질문에 대한 답이 아닐 수 있다. |
| **Faithfulness vs Correctness** | 제공 Context와 일치해도 원본 자료가 오래되거나 틀리면 실제 정답과 다를 수 있다. |
| **Citation vs Grounding** | Citation은 출처 ID, Grounding은 본문 주장의 실제 근거 일치 여부. |
| **Trace vs Evaluation** | Trace는 실행 기록, Evaluation은 기준에 따른 품질 채점. |
| **Quality Gate 통과 vs 배포 승인** | 교육용 1차 Gate를 통과해도 생성 품질·보안·운영 검토가 남는다. |

# K. 프로그램 코드 없이 한 문장으로 전체 작동 방식 설명하기

평가 담당자는 먼저 질문과 **어떤 문서를 찾아야 하는지에 대한 정답(Gold)**, **어떤 내용으로 답해야 하는지에 대한 정답(Reference Answer)**을 정해 둔다. 그 뒤 평가용 실행 담당이 **정답은 보여 주지 않은 채** 기존 RAG 서비스에 질문을 입력한다. RAG는 질문을 정리하고 관련 문서 후보를 검색하며, 후보 순위를 재정렬한 뒤 실제 근거를 골라 LLM에게 전달한다. LLM이 답변을 생성하면 서비스는 형식과 출처를 검사한다. 이 과정의 **후보 문서 ID, 실제 Context ID, 답변, 상태, 시간**을 평가 기록으로 남긴다. 평가기는 그 결과를 미리 정한 Gold·Reference와 비교해 **Recall·Precision·MRR·nDCG·Faithfulness·Relevance·Correctness** 등을 계산한다. 마지막으로 평가자는 실패한 질문을 분석해 **Retriever를 고칠지, Reranker를 고칠지, Prompt·LLM 또는 Validator를 고칠지** 판단하고, 같은 조건에서 개선 전후를 비교해 보고서를 만든다. 기준을 통과해야 후속 Agent Tool 연결을 검토할 수 있다.

# M. 30초 요약 및 원본 자료에 관한 주의

## 30초 핵심 요약

- **Day28 = 기존 RAG를 실행해 성능을 시험하고, 실패 지점을 찾아 고치는 과정.**
- **전체 평가 흐름 = Dataset → Target Runner → Evaluator → Report → Quality Gate.**
- **Gold는 검색 정답 문서, Reference는 생성 답변의 기준 정답.**
- **Gold는 검색이나 LLM 입력에 전달하지 않는다.**
- **Recall·Precision·Hit은 정답 포함 여부, MRR·nDCG는 순위를 평가한다.**
- **Faithfulness·Relevance·Correctness·Citation은 각각 다른 대상을 비교한다.**
- **정답이 후보에 없다면 Retriever, 후보는 있으나 순위가 낮다면 Reranker, 근거가 있는데 답이 틀리면 Generator를 우선 살펴본다.**
- **점수뿐 아니라 Latency·오류·권한·사람 검수도 보고 다음 단계 진행을 결정한다.**

## 원본 범위·신뢰도 구분

1. 이 문서는 사용자가 제공한 `Day28_RAG_Evaluation_Debugging_정리.md`의 **8개 챕터, 예시 산출물, 용어집, 핵심요약**을 기준으로 재구성했다.
2. 원본의 인터랙티브 데모는 **교육용 고정 시뮬레이션**이다. 설명의 순위·Latency·Claim 판정값은 실제 모델·PostgreSQL·GPU 측정치가 아니다.
3. 원본의 일부 평가 실행 연결부는 **추후 구현할 부분**으로 남아 있다. 특히 `build_evaluation_target()`은 그대로 실행 가능한 완성본이 아니다. 실제 RAG·Trace 연결을 완성해야 실측 평가가 가능하다.
4. LangSmith는 선택 사항이다. **로컬 Python 평가 함수와 JSON/CSV/JSONL로도 평가할 수 있다.**
5. 수업의 Quality Gate 임계값은 **서로 다른 교육용 정책 예시**이며 실제 서비스의 합격 기준을 의미하지 않는다.
6. 본 문서는 기본 개념과 실행 순서 이해를 위한 노트다. 사용자가 요청한 초보자용 학습 목적에 맞춰 복잡한 코드보다 **동작 원리, 데이터 전달, 지표 계산, 실수하기 쉬운 구분**에 집중했다.
