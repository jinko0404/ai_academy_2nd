RAG Evaluation 시스템
	- 기존 RAG 시스템의 성능을 평가하고 개선하기 위해 검색 성능, 검색 순위, 답변 품질 및 시스템 실행 상태를 여러 평가 지표를 통해 평가하는 시스템이다.

1. Evaluation Dataset을 준비한다.
	- RAG의 성능을 평가하기 위한 시험 문제와 정답지를 준비하는 과정이다.
	- 사람이 평가에 필요한 질문을 미리 준비하여, 질문에 답변하기 위한 Chunk ID를 지정한다.
	- 사람이 직접 미리 지정한 정답 근거 문서를 Gold 라고한다.
	- Gold는 올바르게 검색했는지 평가하기 위한 정답 문서다.
	- 답변이 정확한지 평가하기 위한 참조 답변을 Reference Answer라고 한다.
	- 문서마다 질문과 얼마나 관련이 있는지 관련성 등급도 지정이 가능하다.

1-1. No-answer 질문을 구분한다.
	- 모든 질문에 반드시 정답 문서가 존재하는 것은 아니다.
	- 이 경우 RAG가 억지로 답변을 생성하는 것이 아니라 근거 자료가 부족하다고 답변하는 것이 적절하다.
	- 이러한 질문은 일반적인 검색 성능 점수와 분리하여 평가한다.

2. 평가용 질문을 Target에 전달한다.
	- Target이란 RAG Evaluation 시스템이 성능을 평가하려는 기존 RAG 시스템을 의미한다.
	- Target 에게 질문 번호, 질문 내용, 카테고리, 이전 대화 기록(history)만 전달한다.
	- 정답지를 미리 전달하면 재대로된 성능 평가가 불가능하기 때문에 Gold 문서 ID나 Reference Answer는 전달하지 않는다.
	- Gold 문서 ID나 Reference Answer가 전달 되는 것을 Gold Leakage(정답 데이터 유출)이라고 한다.

3. 기존 RAG 시스템을 실행하고 실행 기록을 수집한다.
	- LangChain의 invoke()를 통해 평가 대상인 RAG 시스템을 실행하고 최종답변과 중간 과정에서 발생한 실행 기록을 수집한다.
	- 이렇게 수집된 기록들을 Trace라고한다.
	- 해당 기록을 통해 어떤 단계에서 문제가 발생하였는지 진단이 가능하다.

4. Retrieval Evaluation을 통해 검색 성능을 평가한다.
	- RAG가 검색한 문서 ID와 Gold 문서 ID를 비교하여 필요한 문서를 얼마나 잘 찾았는지 평가하는 과정이다.
	- 여기서 Recall, Precision, Hit이라는 지표가 평가에 사용되며 검색 범위(Top-k)를 지정한다.
		- Recall: 전체 정답 문서 중 얼마나 많이 찾았는가?
		- Precision: 검색 범위(Top-k) 내의 정답 문서가 얼마나 포함 되어있는가?
		- Hit 정답 문서를 하나라도 찾았는가?(True/False)
		* Top-k는 검색 결과 중 상위 몇 개를 평가할 것인지 의미한다.

5. Ranking Evaluation을 통해 검색 순위의 품질을 평가한다.
	- 필요한 문서를 찾았다 해서 검색 성능이 무조건 좋은 것은 아니다.
	-  정답 문서가 뒤쪽에 위치하면 Context Builder에서 제외되어 LLM에게 전달이 안될 수 있기 때문이다.
	-  이에 따라 정답 문서가 얼마나 높은 순위에 위치해 있는지도 평가하는데 여기서 쓰이는 지표는 아래와 같다.
		- RR: 첫번째 정답 문서가 얼마나 앞에 있는가?
		- MRR: 여러 질문의 RR 점수의 평균 값
		- DCG: 문서의 관련성 등급과 검색 순위를 함께 평가
		- nDCG: 실제 검색 순서가 이상적인 순서에 얼마나 가까운가?

* Retrieval Evaluation은 정답 문서를 잘 찾았는지 평가하고 Ranking Evaluation은 정답 문서를 좋은 순서로 배치했는지 평가한다.

6. Generation Evaluation을 통해 답변 품질을 평가한다.
	- 검색 성능이 좋아도 LLM이 잘못된 답변을 생성할 수 있기에 LLM의 답변도 따로 평가해야한다.
	- 평가 기준은 아래와 같다.
		- Faithfulness: 근거에 충실한 답변인지 Context와 답변을 비교한다.
		- Relevance: 질문에 적합한 답변인지 질문과 답변을 비교한다.
		- Correctness: 사실에 맞는 정답인지 Reference Answer와 답변을 비교한다.

6-1. 답변을 Claim 단위로 나누어평가한다.
	- Claim은 답변에 포함된 개별적 주장을 의미한다.
		* 근거가 뒷받침된 Claim / 전체 Claim = Faithfulness

7. Failure Diagnosis(실패 원인 진단) - 실패의 원인을 분석하고 문제 발생 위치를 찾아낸다.
	- 평가 결과가 좋지 않다면 RAG 시스템의 어떤 단계에서 문제가 발생했는지 진단한다.
	- 해당 과정에서 Trace가 활용된다. 실패 위치를 구분해야 수정해야할 부분을 바로 알 수 있다.

8. Debug Comparison(디버그 비교) - 개선 전후의 성능을 비교한다.
	- 실패 원인과 위치를 확인하고 RAG를 개선했다면 실제로 성능이 향상되었는지 확인한다.
	- 동일한 평가 데이터로 개선 전후의 RAG 시스템을 실행하고 평가 지표를 비교한다.

9. Quality Report(품질 보고서)를 통해 전체 평가 결과를 정리한다.
	- 지금 까지 평가한 여러 질문의 결과를 하나로 합쳐 전체 RAG 성능을 확인할 수 있는 보고서를 작성한다.
	- 보고서 내용에는 다음과 같은 정보를 표기하면 된다.
		- 평균 Recall, Precision, Hit, MRR, nDCG
		- 출처 정보의 유효성
		- 시스템 실행 실패 건수
		- No-answer 질문의 적절한 답변 거절 여부
		- 질문별 실행 시간과 답변 정보
		- 평가 데이터 버전 및 실행 모드
	- 이 때 정답 자체가 존재하지 않는 No-answer 질문은 일반 검색 성능 평균에서 제외하고 별도로 관리해야한다.

10. Quality Gate를 통해 Agent 연결 가능 여부를 검토한다.
	- RAG 구축과 평가를 모두 완료했다면 해당 RAG를 AI Agent가 사용할 수 있는 Tool로 연결할 준비가 되었는지 확인한다.
	- 평균 Recall, MRR, 출처 검증 실패 건수, 시스템 실행 실패 건수, 사람의 답변 검수 통과 여부, 접근 권한 검사 통과 여부 등등의
	기준들에 부합하는지 검토하는데 이러한 검토 과정을 Quality Gate라고 한다.
	- 검색 성능 뿐 아니라 권한, 안전, 답변의 신뢰성 등등도 검토해야한다.

종합적으로 RAG Evaluation의 전체 흐름은 RAG의 실행 기록을 수집하고, 사람이 준비한 정답 데이터와 비교하여 성능을 평가하고, 문제가 발생한 위치를 파악하여 시스템을 개선한다는 것이다.
